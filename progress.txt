# Ralph Progress Log
## Codebase Patterns
- When the repo root is both `[package]` and `[workspace]`, use `cargo test --workspace` to run member-crate tests (plain `cargo test` only targets the default package).
- For `#![no_std]` crates that still want unit tests/doctests, add `#[cfg(test)] extern crate std;`.
- In `src/parser/plc.pest`, when an alternation allows both `measured_value` (e.g. `50bar`) and `number`, list `measured_value` first so `50bar` doesn't partially match as `50`.
- In `src/parser/plc.pest`, when `number` and `integer` are both allowed, list `number` before `integer` to avoid `2.0` being partially consumed as `2`.
- In PLC topology `analog_input { range: A..B }`, the DSL range syntax does not support negative bounds; if you need signed values, model them as offset-encoded (or split sign into a separate discrete signal) and keep `range` non-negative.
- In `if: <cond> goto ... else: goto ...`, `goto` targets must be a task name or `task.step` (step-only names are treated as task names); when branching within the same task, use `goto cycle.<step_name>`.
- Safety rules that relate an unconstrained `external: true` analog input (e.g. `zone_code`) to an actuator state can be unverifiable/unsatisfiable unless the actuator state is unreachable or you model assumptions about the external signal's behavior.
- For multi-coordinate axis setups (count/theta/pos_mm), pick exactly one “primary truth” coordinate; keep conversion + consistency checks in the driver layer and expose discrete health signals (`range_valid`, `pos_consistent`, optional `health_code`) to the DSL.
- In `runtime-core`, `delay`/`timeout` are evaluated as `elapsed = now_tick - step_entered_tick`, and they fire when `elapsed >= configured_ticks` (so `after_ticks: 0` is immediate on the entry tick).
- In `crates/sim::SimIo`, input changes scheduled for tick `N` are applied when `advance_tick()` moves to `N`, so they are visible during the runtime's tick-`N` evaluation (tick-0 changes are applied in `SimIo::new`).
- For reusable `.plc` templates meant to run via `runtime_bridge`, include explicit physical IO devices (`X<N>`, `Y<N>`) plus logical devices connected via `connected_to`, so IO IDs resolve deterministically.
- In `TopologyGraph`, `device A { connected_to: B }` creates an edge `B -> A` (upstream to downstream). For scenario/IO mapping helpers, start from physical IO nodes (`X<N>`, `AI<N>`) and follow outgoing neighbors to discover logical aliases.
- Scenario YAMLs generated by `scenario-init` include a `# Source PLC: <name>` header; use it (or validate it) to catch PLC/scenario mismatches early.
- For per-example scenario suites, store them under `scenarios/<example_stem>/` and regression-test them by running `scenario-validate` + `sim-plc` and asserting presence/absence of `"reason":"timeout"` events in the produced trace.
- If you want scenario YAMLs to reference logical analog input aliases by name, ensure the PLC topology models `connected_to` chains from physical `AI<N>` nodes to logical `analog_input` devices (and semantic connection typing allows analog<->analog logical connections).
- For CLI-driven docs, add a doc consistency test that checks required commands are present both in the markdown playbook and in `rust_plc` usage output.
- For docs with fenced ` ```plc` snippets, keep each snippet a complete PLC file (`[topology]` + `[constraints]` + `[tasks]` in order) and add an integration test that extracts and parses those blocks via `parse_plc` to prevent example drift.
- For repo-local Wiki drafts under `docs/wiki/`, include at least one complete ` ```plc` snippet and gate it with a small test (extract + `parse_plc`) so drafts don't silently drift into non-parseable examples.
- For scope-sensitive deliverables, add an explicit “in-scope vs out-of-scope” section in the canonical doc and lock key boundary phrases with a doc regression test to avoid implicit capability creep.
- For doc deliverables with structural acceptance criteria (required headings/links), add a lightweight regression test that asserts those key strings exist to prevent drift.
- For JSONL contracts that are diff-sensitive, serialize typed structs (not maps) and keep canonical field declaration order so snapshots stay stable.
- For percentile-based gates/reports, use one deterministic nearest-rank rule and lock it with unit tests so threshold behavior stays stable across refactors.
- For `crates/sim` plant-style dynamics, keep the plant as a deterministic tick-step that *returns* input updates, and call it from `SimIo::advance_tick()` (after applying scenario inputs) to avoid borrow-checker pitfalls with `&mut self` callbacks.
- For scenario-side burst generators, enforce tick alignment on `at_ms/period_ms/active_ms` at parse time so replay behavior stays deterministic and seed-independent.
- For discrete dead-time models, use a fixed-length FIFO with `delay_ticks = ceil(dead_time_ms / tick_ms)` so response timing stays deterministic across runs.
- Waveform exports are deterministic by construction: VCD assigns idcodes in a fixed order (`di<N>` then `do<N>`) and uses timestamps `tick * tick_ms` with `$timescale 1ms`.
- For human-friendly YAML parse errors, use `serde_path_to_error` so errors include a field path (e.g., `inputs[0].set.digital_inputs`).
- `serde_yaml` enum representations can be surprising (it expects YAML tags like `!Variant`); for author-friendly scenario files prefer struct-shaped keys like `faults: - sensor_stuck: { at_ms, target, value }`.
- To unit-test verifier behavior that semantic validation would normally reject (e.g., "skipped rule binding"), build constraints normally and then mutate `ConstraintSet` inside the test.
- `src/runtime_bridge.rs` builds `runtime-core::Program<'static>` by leaking boxed slices/strings (`Box::leak`) to keep the runtime API simple for now; treat this as OK for CLI/tests but avoid in long-lived processes.
- The repo is not currently rustfmt-clean; treat `cargo fmt --check` as non-gating unless you are intentionally doing a formatting pass.
- CLI integration tests in this repo should invoke the compiled binary via `env!("CARGO_BIN_EXE_rust_plc")` and verify artifacts on disk.
- The main `<file.plc>` CLI now writes a structured verification report to `out/<stem>.verification_report.json` by default; in tests prefer `--report <temp-file>` to avoid shared output collisions.
- Runtime budget warnings should update `runtime_budget` data before report serialization, so JSON evidence and stderr/deny-warnings behavior stay consistent.
- Batch SIL regress runs live in `rust_plc::sim_regress`: it scans `.plc`/scenario YAMLs recursively, writes per-case `trace.jsonl`/`report.json` under `out/sim-regress/case_XXXX`, and emits a summary JSON.
- No-board trace regression gate is available as `rust_plc no-board-gate`: it runs SIL + `virtual-board` + `trace-diff` and writes `sil_trace.jsonl`, `board.log`, `board_trace.jsonl`, `diff_report.json` under `--out-dir`.
- `no-board-gate` can reuse `tick_timing.jsonl` to enforce realtime thresholds (`--max-p99-exec-us`, `--max-overrun-count`) while keeping trace-diff gating unchanged when thresholds are unset.
- For embedded workspace crates, keep a host-stub `main()` behind `cfg(not(target_os = "none"))` so `cargo test --workspace` stays green while firmware code is `cfg(target_os = "none")`.
- In embedded crates with host-stub builds, gate firmware-only helpers with `#[cfg(any(test, target_os = "none"))]` so `cargo check --workspace` stays warning-clean on host.
- Release-style artifacts should include a `manifest.json` that hashes the exact on-disk files (plus `size_bytes`) so integration tests can verify integrity deterministically.
- When release-bundle adds new evidence artifacts, add them to both manifest hashing and integration-test required lists in the same change to keep delivery contracts auditable.
- For example safety-modeling fixtures, assert `verification.safety.rule_statuses` contains one entry per safety rule and keep `skipped_rules == 0` to catch silently unbound constraints.
- For board text log parsing, use `line.find("TRACE ")` / `line.find("TIMING ")` to tolerate prefixed logs, parse unordered `k=v` tokens, ignore unknown fields, and report missing/invalid required fields with source line numbers.
- Prefer `rust_plc::board_log::parse_board_log_text` as the single entrypoint for mixed `board.log` parsing (TRACE + TIMING), and keep record-specific parsers in `board_trace` / `tick_timing`.
