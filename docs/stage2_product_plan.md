# RustPLC 下一阶段产品化落地报告（Stage 2）

日期：2026-02-18  
适用分支基线：`master@976d436`

---

## 1. 报告目标

本报告用于规划 RustPLC 在“功能可用”之后的下一阶段：从研发导向工具，升级为可规模化落地的工程产品。  
核心要求：**可用、可靠、可维护、可推广**，并形成稳定的交付与迭代节奏。

---

## 2. 当前阶段成果（已具备）

结合当前代码与文档，RustPLC 已具备以下能力：

1. **核心编译与验证链路**：DSL -> IR -> 状态机 -> runtime 程序 + 验证报告。  
2. **场景体系（M1-M5）**：
   - `scenario-init` / `scenario-validate` / `scenario-expand`
   - 设备名写法 + pulse/hold 语法糖
   - `scenario-gen` 参数化批量生成
   - `sim-regress --minimize-failure` 失败最小化
3. **仿真与门禁**：`sim-plc`、`virtual-board`、`no-board-gate`、`release-bundle`。
4. **RP2040 工程化链路**：build/flash/trace/diff + CI 基础能力。
5. **文档与回归测试基础**：README、playbook、wiki command tests、workspace 测试矩阵。

**结论**：技术闭环已经成型，但“产品体验与规模化采用”仍有明显提升空间。

---

## 3. 下一阶段产品目标（North Star）

### 3.1 产品北极星

> 让一线自动化/测试工程师在 **1 天内完成首个可回归项目搭建**，并在 **1 周内稳定接入 CI 门禁**。

### 3.2 关键成功指标（建议）

1. **Onboarding 成功率**：新用户按文档一次跑通率 >= 90%。
2. **首个项目时间**：从安装到首个 no-board-gate 通过 <= 2 小时。
3. **回归稳定性**：默认模板回归 flake rate < 2%。
4. **问题定位效率**：常见失败（场景/拓扑/实时门限）平均定位时间下降 50%。
5. **发布质量**：每个 release 必须包含可审计 artifacts + 兼容性说明。

---

## 4. 主要差距（问题清单）

### 4.1 用户体验差距

- CLI 错误仍偏工程内部视角，缺少统一错误码和“下一步操作”模板。
- 场景编写仍较复杂，参数空间大时易出现“会跑但不合理”的用例。
- 文档分散，用户不易快速建立“我该先做什么，失败后怎么办”的心智模型。

### 4.2 工程化差距

- 缺少更清晰的版本兼容策略（DSL/schema/artifacts）。
- 缺少性能/稳定性趋势可视化（只给当次结果，缺历史对比）。
- 插件化生态不足（IDE 支持、项目脚手架、团队模板管理）。

### 4.3 产品化差距

- 角色化视图不足（研发、测试、集成商、教学用户诉求不同）。
- 缺少“产品级发行包”与部署方案（单二进制、容器、离线包）。
- 缺少可观测运营数据（匿名、可选）来指导迭代优先级。

## 5. Stage 2 里程碑规划（建议 12~16 周）

## M6（第 1-3 周）：体验硬化（UX Hardening）

### 目标
让首次使用和常见故障处理明显更顺。

### 重点交付
1. **统一错误体系**
   - 引入错误码（如 `SCN-001`, `SIM-002`, `GATE-003`）
   - 每类错误提供固定“原因 + 修复 + 示例命令”
2. **`scenario-doctor` 命令**（新）
   - 自动检查路径、tick 对齐、潜在 same-tick loop、设备名映射、常见误配
   - 支持 `--fix-preview` 输出建议 patch
3. **CLI 输出双模式标准化**
   - `--output human|json`
   - CI 默认 JSON，交互默认 human

### 验收
- 常见 20 个错误场景都有稳定提示模板与测试。
- 用户无需阅读源码即可完成 80% 常见修复。

---

## M7（第 4-6 周）：场景工程化（Scenario Engineering）

### 目标
把“场景编写”从手工 YAML 升级为可管理、可复用、可演进的资产。

### 重点交付
1. **场景模板仓库机制**
   - 项目级模板目录（支持团队自定义）
   - 模板元信息（适用 PLC 类型、覆盖目标、风险标签）
2. **`scenario-gen` 增强**
   - 覆盖策略：pairwise / boundary-first / risk-first
   - `--dry-run` 输出将生成的组合与覆盖统计
3. **失败回灌自动建议增强**
   - 从 minimized case 反推“应更新哪个模板/参数”
   - 输出结构化 `feedback.json`

### 验收
- 典型项目的场景维护成本下降（模板复用率 >= 60%）。
- 批量场景数量可控且覆盖度可解释。

---

## M8（第 7-9 周）：质量门禁产品化（Quality Gate Productization）

### 目标
让门禁不仅能“拦截”，还能“解释趋势与风险”。

### 重点交付
1. **Gate Report Dashboard（HTML + JSON）**
   - trace 一致性、实时指标、失败聚类、最近 N 次趋势
2. **基线管理机制**
   - 基线版本号 + 更新审批流程（防止误放宽）
3. **PR 级快速门禁预设**
   - fast / standard / strict 三档

### 验收
- CI 失败时可在 5 分钟内定位到具体风险来源。
- 团队可审计“阈值为何变化”。

---

## M9（第 10-12 周）：开发者平台能力（DevEx）

### 目标
把 RustPLC 打造成“团队可持续开发平台”。

### 重点交付
1. **`rust_plc new` 项目脚手架**
   - 一键生成目录、示例 `.plc`、scenario、CI 配置
2. **VS Code 扩展（最小可用）**
   - 语法高亮、基础诊断、命令入口
3. **配置版本契约**
   - scenario schema version + 自动迁移提示

### 验收
- 新项目从 0 到 CI 门禁接入 <= 1 小时。
- 常见 DSL/scenario 错误可在编辑器中提前发现。

---

## M10（第 13-16 周）：发行与商业化准备（Release Readiness）

### 目标
形成可对外推广的稳定发行节奏与支持体系。

### 重点交付
1. **发布通道**：stable / preview
2. **兼容性政策**：SemVer + breaking change 清单
3. **产品化文档包**
   - 快速上手、运维手册、迁移指南、FAQ、排障索引
4. **可选匿名遥测（默认关闭）**
   - 只采集命令级耗时与错误码分布，帮助迭代优先级

### 验收
- 连续两个发布周期无重大回退。
- 文档可支撑独立团队接入与维护。

---

## 6. 跨里程碑架构约束（必须坚持）

1. **确定性优先**：同输入同版本同 seed 必须可复现。  
2. **证据优先**：关键判断必须有 artifact 可审计。  
3. **兼容优先**：默认不破坏已有命令与产物格式。  
4. **可自动化优先**：所有关键流程必须可 CI 化。

## 8. 组织与协作建议

1. **双轨迭代**：
   - Track A：内核能力（runtime/sim/gate）
   - Track B：产品体验（CLI/文档/模板/IDE）
2. **每周固定机制**：
   - 周中：失败案例复盘（minimized_scenario）
   - 周末：模板库更新与回灌
3. **DoD（完成定义）**：
   - 代码 + 测试 + 文档 + 迁移说明 + 示例命令可跑通

---

## 9. 风险与应对

1. **功能膨胀风险**：先保证默认路径简单，再做高级开关。  
2. **CI 时间增长**：分层门禁（fast/standard/nightly），并做缓存与样例分级。  
3. **用户模型分裂**：按 persona 输出差异化文档入口，不强行“一份文档通吃”。  
4. **兼容性债务**：每次 breaking 前提供自动迁移与 deprecation 周期。

---

## 11. 结论

RustPLC 已完成“核心能力打底”。下一阶段的关键不是继续堆功能，而是把能力封装成**稳定体验 + 可维护资产 + 团队协作流程**。  
按照本报告的 M6-M10 推进，可把项目从“技术可用”升级为“可被团队长期采用的优秀产品”。
