# Stage-3 任务详细解释（非专业版）

日期：2026-02-19

> 说明：你说的 P0-1（主干收敛与发布基线）已经完成。本文解释剩余 5 个事项（US-001~US-005）到底要做什么、为什么做。

---

## 先看一页“名词翻译”

为了让非专业读者也能看懂，先把高频词翻译成人话：

- **CI（持续集成）**：
  可以理解成“自动质检流水线”。每次代码改动后，它会自动跑检查，像工厂出厂前质检。

- **Gate（门禁）**：
  质检里的“硬门槛”。没过就不能合并代码。

- **Regression（回归问题）**：
  “修了新问题，老功能却坏了”。

- **Runtime（运行时）**：
  程序正在跑的阶段（不是编写阶段）。

- **IO（输入输出）**：
  PLC 与现场设备交互的信号。输入像“传感器读数”，输出像“给电机/阀门的命令”。

- **Variable（变量）**：
  程序里的“内部记忆值”，比如计数、状态、中间计算结果。

- **Audit（审计日志）**：
  类似“黑匣子记录”。谁在什么时候改了什么，都可追溯。

- **Schema（数据格式契约）**：
  文件结构的“固定模板”。字段名、类型、必填项都要一致。

- **Deterministic Replay（可确定重放）**：
  同样输入重复执行，结果必须一致，便于排查。

- **Commissioning（调试投产前联调）**：
  设备上线前最后一轮“实操演练+确认”。

- **Class-D 异常退出（硬件链路类）**：
  这类异常主要依赖硬件安全链（继电器、刹车、断使能等）保障，不是软件单独能兜住的。

- **VS Code 支持包**：
  给新同事“开箱即用”的编辑器配置，减少手动配置时间。

## US-001：把新能力纳入 CI 硬门禁

### 要做的具体任务

1. 在 CI 里明确加入这批新能力对应的测试：
   - online force
   - retain 持久化
   - scenario-gen 覆盖策略/summary 契约
   - sim-regress feedback.json 契约
   - rust_plc new 脚手架
2. 当 `summary.json` / `feedback.json` 的格式漂移时，流水线必须直接失败。
3. 文档里写清楚本地复现命令（开发者在自己电脑可 1:1 复现 CI 失败）。

### 为什么要做

- 现在功能虽然实现了，但如果没有“自动硬门槛”，后续迭代很容易把它们悄悄改坏。
- 门禁的价值是“提前拦截”，防止问题进入主分支后才被现场发现。

### 不做的风险

- 新功能会出现“今天能用，明天被别人改坏”的情况。
- 团队会越来越依赖人工回归，成本高且不稳定。

## US-002：在线变量控制面（开发态）+ 全审计

### 要做的具体任务

1. 在开发模式下增加“在线改变量”能力（默认关闭，显式开关开启）。
2. 至少支持两类变量：
   - BOOL（开/关，真/假）
   - REAL（实数，比如 12.5）
3. 支持脚本注入并保证 tick 对齐，确保结果可重复。
4. 记录完整审计日志：谁改的、何时改的、从什么值改到什么值。
5. 文档明确边界：开发调试能做什么、生产/硬件路径不能做什么。

### 为什么要做

- 当前更多是 IO 级别调试，排复杂逻辑时仍然不够快。
- 变量级控制能更精确地定位“逻辑判断为什么进错分支”。
- 有审计才能避免“改过但没人承认改过”的不可追责问题。

### 不做的风险

- 复杂问题定位时间会很长，调试效率低。
- 临时调试修改无法追溯，后续复盘困难。

## US-003：Class-D（硬件链）异常退出证据流程标准化

### 要做的具体任务

1. 定义 Class-D 电气实测清单模板（必填字段：触发方式、接线状态、实测结果、结论、执行人）。
2. 扩展现有证据格式校验器，让它能识别并验证 Class-D 人工证据附件。
3. 补充文档：Class-D 如何与现有异常退出矩阵、板级安全说明关联。
4. 加测试：有效/无效 Class-D 证据都要能被正确判定。

### 为什么要做

- Class-D 本质是“硬件安全链”问题，只靠软件日志不能证明安全。
- 必须让“人工实测证据”标准化、可审计，避免口头结论。

### 不做的风险

- 安全结论缺少可审查证据，审核和交付风险很高。
- 同一测试不同人做，结果不可比、不可复核。

## US-004：把 doctor / force / retain / gate 串成一条调试作业流程

### 要做的具体任务

1. 输出一份端到端 playbook（从问题诊断到最终 gate 通过）。
2. 至少提供两条可执行演练流程：
   - 正常启动流程
   - 故障注入与排障流程
3. 每一步写清楚：
   - 用什么命令
   - 看哪个产物文件
   - 什么结果算通过/失败
4. 增加文档一致性测试，防止后续文档命令过期失真。

### 为什么要做

- 现在工具是“有了”，但如果没有统一操作手册，不同工程师会各用各的方法。
- 一条标准流程能显著降低新同事上手成本，也减少现场误操作。

### 不做的风险

- 调试行为高度依赖个人经验，团队不可复制。
- 出问题时排查路径混乱，效率低。

---

## US-005：VS Code 支持从“能用”升级到“好用”

### 要做的具体任务

1. 明确 VS Code 支持包规范：
   - 文件识别/基础高亮策略
   - 常用命令入口（tasks/snippets）
   - 推荐插件
2. `rust_plc new` 生成项目时默认带上这套支持。
3. 写 onboarding 文档（安装、使用、常见问题）。
4. 加集成测试：确认脚手架产物完整且关键命令入口存在。

### 为什么要做

- 现在是“最小可用”，但新人仍要花时间自己配环境。
- 开箱即用能把“第一天到跑通流程”的时间大幅压缩。

### 不做的风险

- 新人入场成本高，体验不一致。
- 团队支持成本上升（重复回答环境配置问题）。

---

## 建议执行顺序（从高到低）

1. **US-001**（先把门禁立住）
2. **US-002**（补核心能力缺口）
3. **US-003**（补高风险安全证据）
4. **US-004**（形成可复制作业流）
5. **US-005**（提升日常开发体验）

这个顺序的原则是：
**先保质量底线（门禁）→ 再补关键能力 → 再固化安全证据 → 再做流程化与体验化。**
