# RustPLC Web UI 需求规格说明书

**项目：** RustPLC Web — 集成开发与诊断环境 (IDDE)
**目标读者：** 编程 Agent（前端实现者）
**技术栈：** React + TypeScript + React Flow + Zustand + Tailwind CSS
**版本：** 1.0 | **日期：** 2026-02-19

---

## 第一章 核心设计哲学

你的首要任务是彻底摒弃传统的仪表盘（Dashboard）范式——那种以侧边导航栏加内容区为骨架、以卡片和列表为主要信息载体的设计——转而构建一个**以拓扑画布为绝对核心**的专业工作台。这个工作台的精神气质应当让 UI 本身退到幕后，让工程师的逻辑设计占据舞台中央。

**视觉与交互风格对标如下：**

| 对标产品 | 借鉴维度 |
| :--- | :--- |
| **Blender 节点编辑器** | 上下文感知的右侧参数面板、节点颜色分类体系、暗色主题的高对比度美学 |
| **Cursor / VS Code** | 多标签页工作区、命令面板（`Ctrl+P`）驱动、极简可折叠侧边栏 |
| **Warp Terminal** | 深色极简 UI、高信息密度、流畅无干扰的交互体验 |
| **ComfyUI** | 大画布工作流、节点内联控件的 UX 模式 |

## 第二章 视觉设计系统

所有 UI 组件必须严格遵循本章定义的设计规范。你应当使用 Tailwind CSS 的 CSS 变量机制来实现主题系统，以便未来可以切换浅色/深色主题。

### 2.1 色彩系统

默认实现**深色主题**。所有颜色通过 CSS 自定义属性（Custom Properties）定义，而非硬编码在组件中。

| 用途 | 颜色值 | 说明 |
| :--- | :--- | :--- |
| 应用背景 | `#1a1a1a` | 最底层背景 |
| 面板/卡片背景 | `#2d2d2d` | 侧边栏、弹窗、属性面板 |
| 画布背景 | `#1e1e1e` | 拓扑画布区域 |
| 主文字色 | `#e0e0e0` | 正文内容 |
| 次要文字色 | `#a0a0a0` | 标签、提示文字 |
| 主强调色 | `#00bcd4` | 主按钮、选中高亮、链接 |
| 成功 / Pass | `#52c41a` | 运行通过、设备在线 |
| 警告 / Warning | `#faad14` | 警告告警 |
| 错误 / Fail | `#f5222d` | 运行失败、严重告警 |
| 信息 / Info | `#1890ff` | 信息提示、无板模式 |
| 运行中 | `#722ed1` | 正在执行的任务 |

### 2.2 排版规范

界面文字使用 **Inter**（优先）或系统默认无衬线字体；所有代码、数字数据、IO 值必须使用等宽字体 **JetBrains Mono**（优先）或 Fira Code。基础字号为 `14px`，所有间距必须是 `4px` 的整数倍。

### 2.3 整体布局架构

整个应用采用**三栏式布局**，三栏均可折叠以最大化画布空间。

├──────────────┬───────────────────────────────┬───────────────────┤
│  左侧边栏    │                               │  右侧属性面板     │
│  (280px)     │      中央主区域               │  (320px)          │
│              │   ┌─────────────────────┐    │                   │
│  - 项目树    │   │  标签页 1 | 标签页 2 │    │  上下文感知：     │

│              │   │   拓扑画布 / 回放   │    │  - 未选中时：     │

## 第三章 核心：拓扑画布系统

本章是整个规格中最重要的部分。你必须使用 **React Flow** (`@xyflow/react`) 作为画布引擎。

### 3.1 自定义节点：可自定义的元器件图形

每一种 PLC 元器件都必须有其专属的视觉图形，而非通用的矩形方块。你需要创建一个 `nodeTypes` 映射对象，将节点类型字符串映射到对应的 React 组件。

你需要实现的最小节点类型集合如下：

| 节点类型 (`type`) | 对应组件 | 图形特征 |
| :--- | :--- | :--- |
| `cylinder` | `CylinderNode` | 气缸 SVG：含活塞杆，伸出/回缩状态可视 |
| `sensor` | `SensorNode` | 传感器 SVG：含状态指示灯（ON/OFF） |
| `switch` | `SwitchNode` | 开关 SVG：含触点状态（闭合/断开） |
| `stepper_pd`（推荐）/`stepper`（兼容别名） | `StepperNode` | 步进电机 SVG：含旋转方向指示 |
| `generic` | `GenericNode` | 通用方块，用于未知类型 |

每个节点组件的实现必须遵循以下规则：

**图形由数据驱动。** 节点的 `data` prop 中包含设备的实时状态（如 `data.status`, `data.value`）。SVG 图形内部元素的颜色、位置、可见性必须根据这些状态值动态变化。例如，当 `data.status === 'extended'` 时，气缸节点的活塞杆 SVG 元素应移动到伸出位置，并改变颜色为激活色。

**节点头部统一。** 每个节点顶部应有一个统一的标题栏，显示节点的 `data.label`（实例名称）和一个颜色编码的状态指示点（LED 风格）。

### 3.2 节点内嵌交互：可切换状态的控件

在"无板仿真模式"（`no-board`）下，特定节点（如传感器、开关）必须在其 SVG 图形内部或下方显示一个交互控件，允许工程师直接在画布上切换该设备的状态。

**实现要点：** 所有嵌入节点内部的可交互 HTML 元素（`<button>`, `<input>` 等）都必须添加 `className="nodrag"`。这是 React Flow 的约定，用于阻止点击这些元素时触发节点的拖拽行为。交互控件触发的事件应通过 Zustand store 的 action 来更新节点状态，并最终通过 API 调用将输入事件注入后端仿真引擎。

### 3.3 上下文参数面板：Blender 风格的属性编辑器

这是实现"不同节点有不同参数"需求的核心机制。

**状态管理方案：** 使用 Zustand 创建一个全局 store，其中必须包含 `nodes`（节点列表）、`edges`（连接列表）和 `selectedNodeId`（当前选中节点的 ID，可为 `null`）。

**联动逻辑：** 在 `<ReactFlow>` 组件上监听 `onSelectionChange` 事件，当用户点击一个节点时，将其 ID 写入 `selectedNodeId`。右侧的 `<PropertiesPanel>` 组件订阅该值，并根据选中节点的 `type` 字段，使用一个分发映射（dispatch map）来渲染对应的参数编辑器组件（如 `<CylinderPropertiesEditor>`, `<SensorPropertiesEditor>`）。当 `selectedNodeId` 为 `null` 时，面板显示画布级别的属性（如拓扑版本、约束状态）。

**参数双向绑定：** 每个专属的参数编辑器组件中的所有输入字段，必须与该节点的 `data` 对象进行双向绑定。用户的任何修改都应通过 Zustand action 实时同步回节点的 `data`，并立即反映在画布的节点图形上。

## 第四章 功能模块规格

本章将 `web_ui_functional_spec.md` 中定义的所有功能页面，重新映射到本 IDDE 架构中。

### 4.1 总览看板 (Dashboard)

总览看板作为应用启动后的默认视图，以一个简洁的信息面板呈现，而非独立的全屏页面。它必须展示：当前项目/场景名称、运行模式（`no_board` / `hil_board` / `runtime_live`，以颜色区分）、最新运行状态（pass/fail/running）、各级别告警数量，以及进入主要功能区（运行、回放、诊断）的快速入口按钮。

### 4.2 拓扑与约束评审 (Topology & Constraints)

这是应用的主视图，以拓扑画布为中心。

**元器件库（左侧边栏）：** 提供按类型分类的元器件列表，支持关键词搜索和标签过滤。用户可以将元器件从库中**拖拽**到中央画布上，从而创建一个新的节点实例。

**拓扑编辑：** 用户可以在画布上连接节点的端口（Handle），创建信号连接（Edge）。连接时必须进行即时校验：端口类型不匹配、方向错误、关键输入悬空时，必须以红色高亮提示。

**保存状态：** 当拓扑存在未保存的更改时，当前标签页的标题必须显示一个明显的标记（如 `●`），顶栏的"保存"按钮必须高亮。在有未保存更改的情况下，用户尝试关闭标签页或触发"提交评审"时，必须弹出拦截提示。

**评审流程：** 拓扑文件具有 `Draft → In Review → Approved → Locked` 的状态流转。当状态为 `Locked` 时，画布必须进入只读模式，所有编辑操作被禁用。用户必须通过"新建版本"操作才能再次编辑。评审结论（通过/驳回）、评论和电子签核信息必须在属性面板中可操作。

### 4.3 场景/配方页 (Scenario/Recipe)

场景页面作为一个独立的标签页打开。它必须支持场景文件的选择与版本切换，以及对场景参数（tick、duration、输入事件、故障注入）的查看与编辑。必须提供一个**可视化时间轴**，以图形方式展示输入事件和故障注入在时间轴上的分布位置。

### 4.4 运行与门禁 (Run & Gate)

运行控制区域集成在顶栏或一个专用的工具栏中。必须支持一键触发 `component-sim`、`no-board-gate`、`commissioning-run`、`trace-doctor` 等操作。每次运行的结果（Run ID、触发人、时间、状态、工件链接、失败原因摘要）必须以列表形式展示，并支持点击展开详情。

### 4.5 Tick 回放审查 (Tick Replay Inspector)

Tick 回放是一个特殊的视图模式，以独立标签页打开。其布局如下：

**底部时间轴（Scrubber）：** 这是回放视图的控制中枢。它是一个可拖动的滑块，范围从 Tick 0 到最大 Tick 数。时间轴上必须以彩色标记点标注关键事件（红点表示异常，蓝点表示预期事件）。必须提供"上一个关键点/下一个关键点"的快捷跳转按钮，以及播放/暂停和速度控制（0.5x / 1x / 2x / 5x）, 再是允许跳转到后端提示的关键点列表。

**画布联动：** 这是回放功能的核心。当用户拖动时间轴滑块时，应用必须根据当前 Tick 的快照数据，**批量更新所有节点的 `data` prop**。这将自动触发所有自定义节点组件的重渲染，使其 SVG 图形反映出该 Tick 的真实状态（例如，气缸在 Tick 42 是伸出的，则画布上的气缸节点 SVG 应显示伸出状态）。

**右侧面板联动：** 回放模式下，右侧属性面板应显示一个 IO 值列表（DI/AI/DO/AO），其值也必须随 Tick 变化而同步更新。同时提供"预期 vs 实际"的 Trace/Diff 对比视图。

> 后端契约对齐说明：  
> - `component-sim` 主输出是组件级状态（`component_trace.jsonl`），并非原生 DI/AI/DO/AO 全量快照。  
> - 若需要 DI/AI/DO/AO 全量回放，需使用 `sim-plc --io-snapshot-out` 产生 `io_snapshot.json`。  
> - UI 必须根据数据源能力自动切换展示（组件视图 / IO 视图），不能假定两者总是同时存在。

### 4.6 离线交互仿真 (Offline Interactive Simulation)

在 `no-board` 调试模式下，画布上的传感器、开关类节点的内嵌交互控件（见 3.2）应处于激活状态。点击这些控件，将触发一个 API 调用，向后端仿真引擎注入一次手动输入事件（等价于 `switch_events` 或 `sensor_events`）。

对于故障注入，必须在节点的右键上下文菜单中提供"注入故障"选项。当前后端原生支持如下：气缸 `jammed`、`motion_timeout`；传感器 `stuck_on`、`stuck_off`、`chatter`；开关 `stuck_on`、`stuck_off`；步进 `lost_step`、`stall`、`direction_reversed`。对于每种注入项，必须显示其能力状态标识（`已原生支持` / `可近似模拟` / `待后端实现`）。所有手动注入操作必须写入审计日志。

### 4.7 寄存器/强制控制 (Override & Register Control)

强制控制功能仅对授权角色（调试工程师及以上）可见。它提供对 DI/AI/DO/AO 的强制写入能力，支持设置持续时间（TTL）和批量操作预览。

**安全保护是强制要求：** 所有强制写入操作都必须经过二次确认弹窗（含风险说明文字），并在弹窗中要求用户输入指定的确认文本（如 `CONFIRM`）。确认按钮必须有 3 秒倒计时，防止误触。与互锁/互斥约束冲突的操作必须被阻止提交。界面上必须以明显的视觉方式（如红色警告横幅）区分"开发态允许"与"生产态禁止"的能力。

### 4.8 告警与诊断中心 (Alarm & Diagnosis)

实时告警通过 HMI/BFF 提供的 WebSocket 通道接收（例如 `/ws/alarms`）。底部状态栏和右上角必须常驻显示告警计数器，按严重级别（Critical/Warning/Info）分色展示。点击计数器展开告警列表面板，提供告警确认（Ack）、关闭（Close）、按时间/级别/关键词筛选等功能。

当一次运行失败后，右侧属性面板应自动切换到"诊断"视图，展示来自 `diagnosis_report.json` 的 Top-N 候选原因，包括 `issue_code`、`confidence` 置信度和 `evidence` 证据。每个 `DIAG-*` 码必须提供人类可读的解释和下一步建议。点击证据条目，应能自动跳转到 Tick 回放视图的对应 Tick 位置。

### 4.9 审计与报告 (Audit & Reports)

审计页面作为独立标签页打开，提供一个标准的数据表格视图，支持按时间范围、操作人、对象、操作类型进行筛选。审计记录必须以只读方式呈现，不允许普通角色删除。必须支持将筛选结果导出为 JSON 或 CSV 格式。

## 第五章 数据契约与 API 规范

前端必须直接消费以下后端工件和接口契约，不得自行发明与后端冲突的数据字段。**第一原则：以后端现有契约为准。**

| 工件/接口 | 用途 | 当前状态 |
| :--- | :--- | :--- |
| `commissioning_index.json` | 步骤状态与工件索引 | 后端已稳定 |
| `diagnosis_report.json` | 候选原因与证据（用于诊断面板） | 后端已稳定 |
| `component_trace.jsonl` | 组件级 Tick 回放数据（驱动画布联动） | 后端已稳定 |
| `fault_audit.jsonl` | 注入异常生命周期审计 | 后端已稳定 |
| `component_diagnosis.json` | 组件异常上下文诊断 | 后端已稳定 |
| `component_keypoints.json` | 关键点跳转列表（可选工件） | 后端已稳定（`component-sim --keypoints-out`） |
| `io_snapshot.json` | DI/AI/DO/AO 回放快照 | 后端已稳定（`sim-plc --io-snapshot-out`） |
| `GET /api/topology/:id` 等 HTTP API | 前端访问后端工件的统一入口 | **建议由 BFF 封装，非 RustPLC 核心稳定契约** |
| `WebSocket /ws/alarms` | 实时告警事件流 | **需由 HMI/BFF 服务提供，RustPLC 本体不内建该服务端点** |
| `WebSocket /ws/run-status` | 运行状态实时推送 | **建议项，当前未纳入 RustPLC 核心稳定契约** |

所有 TypeScript 接口（Interface）定义必须与上述 JSON 工件的字段结构严格对齐。当 WebSocket 连接断开时，前端必须自动降级到轮询模式（`fetch` + `setInterval`）。

> 实施建议：Web UI 团队可实现一层 `BFF`（Backend For Frontend）服务，将 CLI 工件与命令执行包装成 HTTP/WebSocket；但该层接口变化不得反向约束 RustPLC 核心数据契约。

## 第六章 安全与权限

### 6.1 用户角色

| 角色 | 权限范围 |
| :--- | :--- |
| **操作员 (Operator)** | 查看状态、确认告警 |
| **调试工程师 (Engineer)** | 运行调试、查看诊断、申请强制写入 |
| **审核员 (Auditor)** | 审批拓扑变更、电子签核 |
| **管理员 (Admin)** | 用户权限管理、系统配置、审计导出 |

### 6.2 安全硬要求

所有写操作必须携带操作者身份（JWT Token）。高风险操作（强制写入、上线放行）必须有二次确认弹窗和风险说明。审核动作必须与执行动作分离（不能自己提交自己审批）。页面必须以明显的视觉标识区分当前是否处于开发态（允许强制控制等危险能力）。

## 第七章 非功能要求

**页面刷新恢复：** 应用的关键 UI 状态（当前打开的标签页、选中的节点、当前 Tick 位置）必须持久化到 `localStorage` 或 `sessionStorage`，页面刷新后能够恢复。

**大数据量处理：** Tick 回放的时间轴和 IO 列表在处理超过 10 万个 Tick 的数据时，必须使用虚拟化渲染（Virtual Scrolling），避免浏览器卡顿。

**告警限流：** 实时告警展示必须实现前端限流（throttle），避免告警风暴导致 UI 冻结。

**最低浏览器支持：** Chrome 90+、Firefox 88+、Edge 90+。最小分辨率：1280×800。

## 第八章 开发路线图

请严格按照以下阶段顺序进行开发，每个阶段完成后交付可演示的产物。

**Phase 1 — MVP（核心骨架）：** 搭建完整的三栏布局和多标签页框架。实现只读的拓扑画布，能够从 API 加载数据并以自定义 SVG 节点渲染。实现基础的 Tick 回放（可拖动时间轴并驱动节点颜色变化）。

**Phase 2 — 核心功能：** 实现完整的拓扑编辑功能（拖拽创建节点、连线、参数编辑、保存）。实现上下文感知的右侧属性面板（Blender 风格）。实现节点内嵌控件交互和离线仿真注入。实现用户认证与角色权限系统。实现 WebSocket 实时告警。

**Phase 3 — 生产就绪：** 实现完整的拓扑评审与电子签核流程。实现强制控制等高风险操作的完整安全机制。实现审计报告导出。实现有板模式（HIL/Live）支持。
