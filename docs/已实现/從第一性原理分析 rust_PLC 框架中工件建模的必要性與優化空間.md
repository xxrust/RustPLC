# 從第一性原理分析 rust_PLC 框架中工件建模的必要性與優化空間

## 背景

本文不是重新发明一套行业专用 DSL，而是从 RustPLC 当前的架构目标出发，分析为什么“工件建模”应当成为一等语义，以及 RustPLC 在这条线上应当吸收哪些方向、拒绝哪些错误抽象。

RustPLC 当前已经较强地建模了以下几层：

- 设备与拓扑
- task / step / blocking step
- pending action
- safety / liveness / timing / causality verification
- semantic resource / resource claim / action semantic tag

这些能力已经足以表达“机器如何动作”和“机器之间如何避免冲突”。但它们还没有完整回答另一个更接近工艺本质的问题：

- 被加工对象是什么
- 它当前在哪里
- 它经过了哪些步骤
- 它为什么会进入某个分支
- 它是否能从初始位置到达目标位置
- 它是否在任何时刻违反守恒、一致性或独占关系

这正是工件建模要解决的问题。

---

## 第一性原理结论

一个 PLC 控制系统的最终目标，通常不是“让某个气缸伸出去”或“让某个轴转到 90 度”，而是让某个对象在受控约束下完成状态演化。

也就是说：

- 设备是手段
- 动作是机制
- 工件状态演化才是目标

如果 DSL 只能表达设备动作，而不能表达工件的身份、位置、属性、持有关系和状态转移，那么系统最多只能证明“设备动作序列合理”，却很难证明“对象流转正确”。

因此，工件建模不是一个附加功能，而是 RustPLC 从“设备动作描述系统”升级为“工艺语义建模系统”的必要一步。

---

## 总体判断

现有 PLC 建模长期偏向设备与动作，而缺乏对被操作对象的第一类语义建模。这一点是对的，而且对 RustPLC 很有价值。

但文章也有两个明显问题：

1. 它把 `wafer` 当成了核心抽象的天然候选。
2. 它过度把 Rust 的 ownership / typestate 直接等同于 PLC 工件语义的最终承载机制。

所以这篇文章不是不能用，而是要“吸收其方向，修正其落点”。

---

## 可吸收的部分

### 1. 正确指出了“设备导向建模”的盲区

这一点最有价值。

当前主流 PLC 风格通常把以下对象作为建模中心：

- 设备
- I/O
- 动作
- 顺序逻辑

这会导致对象状态只能被间接表达。例如：

- `wafer_on_slide == true`
- `wafer_on_orient == true`
- `vacuum_ok == true`

这些信号可以帮助控制，但它们不是对象语义本身。对象语义应该是：

- 某个工件位于 `slide_pick`
- 某个工件正被 `arm` 持有
- 某个工件已经过 orient 检测
- 某个工件被判定为 reject

如果对象本身没有进入建模主路径，verification 的能力就会停留在“信号和动作层面”。

### 2. 正确强调了“生命周期”比“局部状态位”更重要

文章反复强调对象的生命周期，这一点值得保留。

工件建模的核心不是加几个字段，而是把以下问题统一起来：

- 对象从哪里来
- 对象在各阶段如何转移
- 对象在异常路径中如何结束
- 对象是否可能卡在非法中间态

这类问题如果不进入 IR，就只能靠经验、测试夹具和运行时观察去猜。

### 3. 正确把“可达性证明”拉入讨论范围

文章提出：只有建模了工件，才能证明工件是否可达某个目标位置或分支。

这点非常重要，因为它把工件建模从“代码组织优化”提升到了“verification 目标扩展”。

RustPLC 的长期目标不是单纯让 DSL 能写，而是要让语义进入：

- IR
- verification
- runtime bridge
- runtime

从这个角度看，这个方向判断是成立的。

### 4. 正确意识到“传感器信号不是最终真相”

文章虽然表达还不够严谨，但它已经在试图指出：

- 传感器是观测
- 工件状态才是被建模对象

这条思路应当保留，并进一步明确为架构原则。

---

## 需要纠偏的部分

### 1. 不应把 `wafer` 做成平台内建类型

这是最需要纠正的地方。

`wafer` 是半导体行业工件，不是 RustPLC 平台语义的通用基元。  
如果平台内核直接内建：

- `wafer`
- `cassette`
- `orient_stage`

那么 RustPLC 就会从“通用工业控制建模系统”退化成“半导体专用控制 DSL”。

正确做法应当是：

- 平台内建 `workpiece` 语义框架
- `wafer` 只是用户在某个项目里定义的一种工件 schema

也就是说，核心层提供的是一种通用工件语言，而不是预置行业对象词典。

### 2. 不应把 Rust ownership 直接当成最终语义承载

把 Rust 的 ownership 和 typestate 直接视为最终承载机制，是过于乐观的。

这两种能力当然有启发价值，但不能直接当成 RustPLC 工件语义的最终实现载体，原因有三点：

- RustPLC 的核心语义必须先闭合在 IR，而不是先闭合在 Rust 源码层
- verification、runtime、codegen 都需要消费同一份语义，不能只让 Rust 编译器理解
- 工业控制的对象流转里经常存在有限多实例、并发 task、缓存位、队列位、空位/占位等问题，直接映射成 Rust 线性类型会很快爆炸

所以 Rust 的类型系统可以借鉴，但不能替代 IR 级语义设计。

### 3. 不应把“对象在一个位置”简化成单一 move ownership

工业现场里很多对象关系不是简单的一对一 move：

- holder 中可以为空，也可以有一个工件
- tray / cassette / buffer 里可以有多个槽位
- 一个 station 可能只观测工件而不持有工件
- 两个系统可能对同一工件有不同层次的视图：几何位置、工艺阶段、质量状态

这说明工件建模不能只靠“谁拥有这个对象”来表达，还必须建模：

- location
- holder
- slot
- occupancy
- observation
- transformation

### 4. Typestate 适合作为灵感，不适合作为唯一中心

Typestate 能帮助表达“只能从 A 到 B，不能从 B 直接到 D”，这很有启发。

但如果把整个 PLC 工件系统都做成 typestate 风格，会遇到问题：

- 分支组合爆炸
- 多工件并发爆炸
- 与 runtime 状态同步困难
- 与 ST codegen 或其他目标后端的映射困难

所以 typestate 更适合作为局部设计参考，而不是架构中心。

## RustPLC 应吸收的真正方向

RustPLC 不应该内建 `wafer`，而应内建一套通用工件语义元模型。

这个元模型至少应回答六类问题。

### 1. 工件种类

平台层要允许用户定义工件类型，例如：

- wafer
- panel
- battery_cell
- bottle
- tray_item
- work_order_carrier

平台不理解这些名字背后的行业含义，只理解它们都是 `workpiece_type`。

### 2. 工件实例

系统必须能表达“某个具体工件”。

这不一定要求现场一定有物理 ID，但 verification 语义上必须能区分：

- 一个工件
- 多个工件
- 某类工件的一个抽象 token

否则无法讨论守恒、唯一性与可达性。

### 3. 工件位置与持有关系

这是工件建模的核心。

需要区分：

- location：对象处于哪个工艺位置
- holder：对象被哪个机构持有
- slot：对象位于哪个容器槽位
- observed_at：对象被哪个传感器观测

例如：

- `slide_pick` 是位置
- `arm_vacuum_head` 是 holder
- `cassette.slot[3]` 是 slot
- `wafer_on_slide_sensor` 是 observation

### 4. 工件属性

工件不只是“有没有”，还携带属性。

典型属性包括：

- orientation_class
- size_class
- recipe_class
- quality_state
- inspected
- accepted / rejected

这些属性才是真正驱动分支的上层语义。

### 5. 工件转移与变换

工件不仅会移动，还会被变换。

通用层应支持：

- transfer：从 A 到 B
- acquire / release：被 holder 持有或释放
- transform：翻转、加工、检测、分类、装配
- route：进入某条工艺路径
- dispose：报废、丢弃、移出系统

但到这里还不够。真实工业现场里，工件语义不只是“单件转移”，还经常包含以下几类更高阶演化：

- split：一个工件经过工艺被分裂成多个新工件
- merge：多个工件被组装、封装或聚合成一个新工件
- mount：多个工件固定在一个 carrier / fixture / plate 上形成绑定集合
- unmount：工件从 carrier / fixture 上解绑
- derive：工件加工后生成新的派生工件，同时保留谱系关系
- consume：原始工件被消耗，转化为产出物、半成品或废料

你补充的三个场景，本质上正对应这三类平台级抽象：

- “一根晶棒切成 400 片晶片”不是 `wafer` 特例，而是 `split + lineage + quantity conservation`
- “多个晶棒固定在铁板上，由平台抬升整块铁板实现位置变化”不是夹具细节，而是 `mounted-set + carrier reference frame`
- “多个工件组装成单个工件”不是单独 feature，而是 `merge / assembly / composite workpiece`

这说明 RustPLC 的工件模型如果只支持单 token 搬运，抽象层级仍然不够。

### 6. 工件谱系、分裂与聚合

工件建模必须显式支持谱系关系。

原因很直接：很多工艺不是“对象原样搬运”，而是“对象在流程中被重新定义”。

典型场景包括：

- 晶棒切割成多片晶片
- 大板材切割成多个零件
- 卷料裁切成多个段
- 一个半成品被装配成更高层级成品
- 多个部件被封装成一个模块

这要求平台层能表达：

- parent-child lineage：父工件与子工件的生成关系
- one-to-many split：单工件分裂为多工件
- many-to-one merge：多工件聚合为单工件
- many-to-many remap：一组输入经过工艺变成另一组输出
- residual / byproduct：主产物之外的边料、残料、废料

这里最关键的不是“名字”，而是约束：

- split 之后，父工件是否仍存在，必须被显式定义
- merge 之后，输入工件是继续保留身份，还是被新工件吸收，必须被显式定义
- 任何派生都应保留 lineage，便于 verification、traceability 和异常追踪

对 verification 来说，这层能证明的东西会大幅扩展：

- 某工艺是否满足数量守恒或质量守恒
- 某个子工件是否必然来自合法父工件
- 某个成品是否由完整输入集合装配而成
- 某条异常路径是否会留下未定义归属的残余工件

### 7. 工件集合、载具与参考坐标系

你提到“多个晶棒以不同角度固定在一个铁板上，而平台通过让整个铁板上升实现到位”，这揭示了另一个关键问题：工件的位置不一定是直接控制的，也可能是相对于 carrier/fixture 间接确定的。

这类场景说明平台必须支持：

- carrier：承载多个工件的载具、铁板、托盘、治具、夹板
- mounted workpiece：安装在 carrier 上的工件
- relative pose：工件相对于 carrier 的位置、姿态、角度
- carrier pose：carrier 在设备中的全局位置
- derived global pose：工件全局位置由 `carrier pose + relative pose` 推导

这类建模不是几何求解器，而是语义边界问题。平台至少要能表达：

- 工件是“独立移动”还是“随载具整体移动”
- 一个动作作用在单工件上，还是作用在 carrier 上
- carrier 的位移会同步影响哪些 mounted workpiece
- mounted workpiece 的相对角度、槽位或偏置是否影响后续加工分支

这会带来一些新的通用模式：

- tray / pallet / fixture / plate / frame / reel
- 阵列工件
- 按槽位索引的工件集合
- 同步群移
- 相对位姿驱动的加工选择

因此，工件模型不能只有 `location`，还需要至少区分：

- physical container
- mounting relation
- reference frame
- relative pose
- inherited motion

### 8. 工件属性之外，还需要工件结构

之前文档强调了工件属性，但你补充的场景表明，还必须再向前走一步：某些工件不是原子对象，而是结构化对象。

例如：

- 一个工件由多个子部件组成
- 一个载具上挂载多个工件
- 一个装配件在完成后成为新工件
- 一个原材料在切割后变成工件集合

所以平台层不能只建模“单对象 + 若干属性”，还应支持：

- atomic workpiece：不可再分的基本工件
- composite workpiece：由多个工件组成的复合工件
- collection workpiece：作为集合被操作的一组工件
- mounted set：在共同 reference frame 中受约束的一组工件

这不是数据结构偏好，而是语义需求。因为很多控制动作的真正目标不是“移动一件东西”，而是：

- 移动一组已绑定对象
- 对复合件中的某个子件加工
- 验证组装完整性
- 验证拆分后是否形成完整子集

### 9. 工件不变量

没有不变量，工件建模就没有验证价值。

至少需要：

- 守恒：对象不能无中生有、不能无声消失
- 唯一性：同一工件不能同时位于多个互斥位置
- 容量约束：某 holder / slot / location 的容量有限
- 分支完备性：进入分支后最终必须收敛到合法终态
- 观测一致性：传感器观测与对象状态不能长期矛盾

在引入 split / merge / mounted-set 之后，不变量还必须升级：

- 谱系闭合：每个子工件都能追溯到合法父工件
- 派生守恒：split / merge / consume 过程中的数量、质量或份额约束必须显式定义
- 装配完整性：组装件必须由完整且兼容的输入集合构成
- 载具一致性：mounted workpiece 的全局位置必须与 carrier pose 推导一致
- 群组同步性：随 carrier 运动的工件集合不得出现部分“瞬移”或局部脱节
- 解绑合法性：未显式 unmount 的工件不得脱离 carrier 独立存在
- 终态完备性：被 split / merge / consume 的输入对象，其生命周期终结方式必须显式

## RustPLC 更合理的分层落点

### 1. 平台核心层

这一层内建的应当是通用概念：

- `WorkpieceType`
- `WorkpieceToken`
- `Location`
- `Holder`
- `Slot`
- `Carrier`
- `ReferenceFrame`
- `Transfer`
- `Transform`
- `Lineage`
- `Split`
- `Merge`
- `MountRelation`
- `CompositeWorkpiece`
- `WorkpieceInvariant`

这层不应该出现 `wafer`、`battery`、`panel` 等行业词。

### 2. 领域建模层

这一层由具体项目定义：

- `wafer` 是一种 `WorkpieceType`
- `orient_stage` 是一种 location
- `ir_box` 是一种 terminal location
- `flip_180` 是一种 transform

这一层承载行业语义，但不污染平台核心。

### 3. 工艺流程层

task / step / action 不再只操作设备，也应能操作工件语义。

设备动作仍然存在，但它们不再是终点，而是实现工件转移的执行机制。

例如：

- 轴动作是执行层事实
- “工件从 slide_pick 到 arm_holder”才是工艺层事实

同理：

- “平台抬升铁板”是执行层事实
- “铁板上所有 mounted workpiece 同步进入切割高度”才是工艺层事实

- “刀具完成一次切割”是执行层事实
- “一个母工件分裂为多个子工件并建立谱系”才是工艺层事实

- “夹爪完成装配动作”是执行层事实
- “多个输入工件聚合成一个新工件”才是工艺层事实

### 4. verification 层

verification 不应只检查设备与资源，还应检查工件：

- safety：工件是否进入非法占位或重复占位
- liveness：工件是否最终到达合法终态
- timing：工件在给定路径上是否满足时间约束
- causality：某个分支是否真的由工件属性或观测链路驱动

如果支持 split / merge / carrier，这一层还应进一步覆盖：

- lineage validity：派生链是否合法
- assembly completeness：装配输入是否齐套
- carrier coherence：载具运动与工件全局位置是否一致
- conservation policy：数量、质量、份额或槽位占用规则是否被破坏

## 与现有 semantic resource 的关系

这里必须明确：工件语义不是对 `semantic_resource` 的替代，而是其上层补足。

`semantic_resource` 解决的是：

- 风险区占用
- 机械空间互锁
- 动作语义占用

工件建模解决的是：

- 对象身份
- 对象位置
- 对象属性
- 对象流转
- 对象终态

两者关系应当是：

- resource model 约束“机器能不能这样动”
- workpiece model 约束“对象是否因此正确流转”

这两层组合起来，系统才能真正回答“工艺是否正确”。

---

## 对 `wafer_loader` 这类系统的启发

在 `wafer_loader` 里，真正的一等对象不应是 `wafer` 这个词，而应是以下通用模式：

- 一个工件从输入容器进入系统
- 被某个执行机构拾取
- 被送往中间工位
- 被检测并得到属性
- 根据属性进入不同分支
- 最终被送往目标位、拒收位或异常终态

这说明 `wafer_loader` 实际上暴露的不是“晶圆专用需求”，而是一个非常通用的工件控制范式：

- pick
- place
- inspect
- classify
- route
- reject

所以它非常适合作为 RustPLC 工件语义设计的首个样例，但不应反过来把 `wafer` 固化成平台原语。

## 其他应提前纳入抽象的经典场景

你补充的三种情况已经把范围从“单件搬运”扩展到了“材料演化”。如果平台要做对，还应提前覆盖下面这些经典模式。

### 1. 母材切分

例如：

- 晶棒切成晶片
- 板材冲切成零件
- 卷料裁成段
- 大片玻璃切成小片

抽象本质：

- 一个输入工件派生出多个子工件
- 可能伴随边料、残料、废料
- 需要谱系追踪与守恒规则

### 2. 多工件绑定在统一载具上

例如：

- 多根晶棒固定在铁板上
- 多个零件放在托盘、治具或夹板上
- 多片电芯装在同一 carrier 中同步流转

抽象本质：

- 多个工件共享 carrier reference frame
- carrier 动作引发群体位置变化
- 组内对象具有相对位姿、槽位或角度差异

### 3. 多件组装成单件

例如：

- 多个部件装成模组
- 多张薄片压合成层叠件
- 多颗芯片封装成单个组件

抽象本质：

- 多输入聚合为一个新工件
- 输入件生命周期必须显式终结或转入子部件关系
- 需要验证齐套、兼容性与装配完整性

### 4. 单件拆成“主产物 + 副产物”

例如：

- 切割后产生主件与边料
- 清洗/筛分后产生合格品与不合格品
- 分选后产生多个等级输出

抽象本质：

- 不只是 split，还包括分类与副产物流向
- 终态需要覆盖 reject、scrap、rework、bypass

### 5. 批次与单件并存

例如：

- 一个 lot 进入系统，内部含多个工件
- 一组工件共享配方、批次号或追溯号
- 某些动作作用在批次上，某些动作作用在单件上

抽象本质：

- batch 与 item 是不同层级对象
- 批次属性与单件属性不能混为一谈

### 6. 工件身份在工艺中重定义

例如：

- 原材料经加工后成为半成品
- 半成品经装配后成为成品
- 切割后父工件身份结束，由子工件接续

抽象本质：

- 身份未必始终不变
- 平台需要支持 identity replacement 与 lineage continuity

### 7. 返修、回流与重入

例如：

- 某工件检测失败后返回前工位重工
- 装配失败后拆解回到零件态
- 不合格件进入 rework 路线后重新加入主线

抽象本质：

- 工件路径不是单向 DAG
- 需要显式建模 rework、rollback、re-entry

### 8. 部分可观测、部分不可观测

例如：

- 某工位只能知道“有无工件”，不知道是哪一个
- 某阶段能读到精确 ID，某阶段只能用位置近似
- 某次 split 后子件未全部逐一传感确认

抽象本质：

- 观测模型与对象真相不完全重合
- verification 需要区分“语义状态”和“观测证据”

## 建议的最小语义闭环

如果 RustPLC 要把工件建模做成长期正确的方向，第一版应追求“可验证的最小闭环”，而不是一次性做成超大对象系统。

建议最小闭环包含：

### 1. 用户可定义工件类型

例如：

- 名称
- 离散属性
- 合法初态
- 合法终态

### 2. 用户可定义位置/holder/slot

并声明：

- 容量
- 独占性
- 是否可观测

### 3. action 与工件语义的关联

某些 action 不再只声明设备动作，还声明其工件效果：

- acquire
- release
- transfer
- transform
- classify

### 4. IR 中显式保存工件语义

必须是 IR first-class，而不是 runtime 临时特例。

### 5. verification 对工件进行检查

至少覆盖：

- 唯一性
- 守恒
- 终态可达
- 分支合法性

---

## 明确应拒绝的错误方向

RustPLC 在推进工件建模时，应明确拒绝以下方向：

### 1. 直接内建 `wafer`

这是行业概念下沉到平台核心，长期会污染抽象。

### 2. 仅在 runtime 里偷偷维护工件状态

如果工件语义不进入 IR 和 verification，那么它只是运行期补丁，不是架构能力。

### 3. 继续把对象语义完全压成传感器位

这样只能得到“观测驱动控制”，得不到“对象驱动验证”。

### 4. 把 Rust ownership 当作全部答案

Rust 类型系统有启发，但 RustPLC 的核心问题是 DSL 语义闭合，不是单纯生成一段更安全的 Rust 代码。

### 5. 一开始就追求无界实例和任意复杂属性

这会直接破坏 verification 可控性。第一版必须是有限域、有限位置、有限容量、有限转移。

---

## 最终判断

这篇分析的价值在于，它准确指出了 RustPLC 下一步必须补的缺口：系统缺的不是更多设备动作，而是工件语义。

但它的落点需要修正：

- 不应把 `wafer` 做成核心类型
- 不应把 Rust ownership/typestate 直接当作最终架构
- 不应把工件建模简化成“一个结构体加若干状态”

RustPLC 真正应该吸收的是下面这条主线：

1. 平台核心定义通用 `workpiece language`
2. 行业项目在其上定义 `wafer` 等具体工件类型
3. 工件语义作为 IR 一等对象进入 verification / runtime / codegen
4. 设备动作退回到“实现工件演化的机制层”

如果沿这条路推进，RustPLC 会从“能描述 PLC 行为”进化到“能证明工艺对象流转正确”的系统。  
这一步是架构升级，不是语法糖扩展。

## 对本文的进一步补充

上文主要解决了“为什么 RustPLC 需要工件语义”，但真实工业场景还要求这套语义不能只覆盖“单件搬运”。你补充的三个场景非常关键，它们分别对应三类必须进入平台抽象的通用模式。

### 1. 单工件分裂成多工件

典型例子：

- 一根晶棒切割成数百片晶片
- 一块板材冲裁成多个零件
- 一卷材料分切成多个段

这类问题的本质不是某个行业的 `wafer` 特例，而是通用的 `split` 语义。平台需要能表达：

- 一个父工件如何派生多个子工件
- 父工件在 split 后是终结、保留，还是部分消耗
- split 是否伴随边料、残料、副产物
- 子工件如何继承或重定义属性
- 整个过程如何保留 lineage

如果没有这层语义，系统只能知道“切割刀动作完成了”，却不能证明“产出的子工件集合是完整且合法的”。

### 2. 多工件绑定在同一载具或参考系上

典型例子：

- 多根晶棒以不同角度固定在同一铁板上
- 多个工件放在统一托盘、夹板、治具上
- 多个电芯在同一 carrier 中同步进入加工站

这类问题的本质不是单个工件位置，而是 `carrier + reference frame + mounted set`。

平台至少应能表达：

- 工件是独立移动，还是随 carrier 整体移动
- 工件相对 carrier 的姿态、槽位、角度或偏移
- carrier 的动作如何批量改变 mounted workpiece 的全局位置
- 某个后续工艺是否依赖工件相对位姿，而不是绝对位姿

也就是说，“平台抬升铁板”在执行层是一个动作，但在工艺层真正发生的是“铁板上的整组工件同步进入新的加工坐标”。

### 3. 多工件组装为单工件

典型例子：

- 多个零件装配为一个模块
- 多层材料压合成一个复合件
- 多个半成品封装为一个成品

这类问题的本质是 `merge / assembly / composite workpiece`。

平台必须能回答：

- 哪些输入工件构成装配输入集
- 它们在 merge 后是消失、成为子部件，还是被新身份吸收
- 装配是否要求齐套、顺序、兼容性和数量约束
- 成品如何保留对输入件的谱系追踪

没有这层语义，系统只能证明“夹爪做了装配动作”，却不能证明“成品是由完整且兼容的输入集构成的”。

### 4. 应补充到平台抽象中的其他经典模式

除了 split / carrier / merge，还应提前考虑下面这些通用模式：

- 主产物与副产物并存：一个工艺可能同时生成成品、边料、废料、返修件
- batch 与 item 并存：有些动作作用在整批工件上，有些动作只作用于单件
- 工件身份重定义：原材料经过加工后变成新的半成品或成品
- 返修与重入：工件可能回流到前工位而不是单向流转
- 部分可观测：系统可能只知道“这里有工件”，但不知道“是哪一个工件”

这说明 RustPLC 的工件语言至少要覆盖四条主线：

- object identity
- object lineage
- object grouping
- object reference frame

### 5. 对最小闭环的修正

基于这些补充，最小闭环不应只支持：

- transfer
- acquire / release
- transform

还至少应为以下语义留出入口：

- split
- merge
- mount / unmount
- derive / consume
- lineage validity
- carrier coherence

这并不意味着第一版就要做复杂几何求解。更合理的策略仍然是：

- 有限槽位
- 有限 carrier
- 离散姿态类
- 有界 split / merge 规则
- 先做语义守恒，再做复杂几何

### 6. 更高层的抽象结论

工件建模不只是“对象在不同位置之间移动”，而应被提升为：

- 对象的生成
- 对象的派生
- 对象的组合
- 对象的挂载
- 对象的消耗
- 对象的终结

换句话说，RustPLC 要建模的不是“物体轨迹”，而是“材料与对象在工艺中的演化关系”。

这一步一旦成立，`wafer`、`rod`、`tray_item`、`battery_cell`、`assembly_module` 都只会成为同一套通用框架下的不同领域实例，而不会反向污染核心平台语义。

## 一句话结论

问题抓对了，但抽象层还不够稳。  
RustPLC 应该内建的不是 `wafer`，而是 `workpiece` 语义框架；`wafer` 只是该框架在半导体场景下的一个实例化。
