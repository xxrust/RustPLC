## 1. 问题陈述

### 1.1 当前代码生成能力的缺口

| 问题 | 严重度 | 代码位置 |
|---|---|---|
| `crates/codegen` 只生成 Rust 静态模块（面向 runtime-core），不生成任何 ST 代码 | 🔴 高 | `crates/codegen/src/lib.rs` |
| 无 IEC 61131-3 ST 生成器，验证通过的逻辑无法部署到任何商业 PLC | 🔴 高 | — |
| `StateMachine` IR 与 ST `CASE` 状态机之间无映射层 | 🔴 高 | `src/ir/mod.rs` |
| `TON` 定时器实例化规则未定义，`timeout`/`delay` 无法生成 ST | 🔴 高 | `src/ir/mod.rs:TransitionGuard` |
| I/O 地址命名约定未定义，设备名到 ST 变量名的映射规则缺失 | 🟠 中 | `src/ir/mod.rs:TopologyGraph` |
| `parallel`/`race` 块无 ST 对应原语，映射策略未定义 | 🟡 低（阶段 1 排除） | `src/ast/mod.rs:ParallelBlock` |

### 1.2 为什么阶段 1 只处理顺序逻辑

PLC 的执行模型是循环扫描：每个扫描周期内所有变量同时有效，同一周期内对多个输出变量赋值，对外部设备来说就是同时发出的指令。

`parallel`/`race` 块的分支同步语义需要额外的状态变量：
- `parallel`：每个分支需要独立的完成标志，全部置位后才能推进
- `race`：需要检测首个完成的分支，并使其余分支的等待条件失效

阶段 1 先打通顺序逻辑核心链路，`parallel`/`race` 的同步语义映射在阶段 3 专项处理。

### 1.3 为什么选 OpenPLC 作为阶段 1 的验证目标

| 维度 | OpenPLC | 基恩士 KV STUDIO |
|---|---|---|
| 变量声明 | 支持代码内 `VAR...END_VAR` | 必须在外部变量表预定义 |
| 标准符合度 | 严格遵循 IEC 61131-3 | 私有方言，有限制 |
| 自动化测试 | 可脚本化编译和执行 | 依赖 GUI 工具 |
| 硬件依赖 | 无（PC/树莓派可运行） | 需要真实 KV 系列硬件 |
| 开源 | 是 | 否 |

OpenPLC 作为**中间验证层**，用于验证 ST 生成的逻辑回归正确性，不依赖任何商业 PLC 硬件。基恩士适配在阶段 3 处理。

## 2. IR 到 ST 的映射设计

### 2.1 总体映射策略

RustPLC 的 `StateMachine` IR 是一个显式状态机（states + transitions）。ST 的标准实现方式是 `CASE` 语句驱动的状态变量。映射关系如下：

| IR 结构 | ST 映射 |
|---|---|
| `StateMachine.states` | `INT` 状态变量的取值集合（枚举常量） |
| `StateMachine.initial` | 状态变量初始值 |
| `Transition.from` | `CASE` 分支的匹配值 |
| `Transition.guard: Always` | 无条件执行，直接跳转（`_state := <next_id>;`） |
| `Transition.guard: Condition { expression }` | `IF ... THEN _state := <next_id>; END_IF` |
| `Transition.guard: Timeout { duration_ms }` | `TON` 实例 + `IF timer.Q THEN _state := <next_id>; END_IF` |
| `Transition.guard: Delay { duration_ms }` | `TON` 实例 + `IF timer.Q THEN _state := <next_id>; END_IF` |
| `TransitionAction::Extend { target }` | `<target>_cmd := TRUE;` |
| `TransitionAction::Retract { target }` | `<target>_cmd := FALSE;` |
| `TransitionAction::Set { target, value: On }` | `<target> := TRUE;` |
| `TransitionAction::Set { target, value: Off }` | `<target> := FALSE;` |
| `TransitionAction::SetAnalog { target, value }` | `<target> := <value>;` |
| `TransitionAction::Log { message }` | 注释行（`(* LOG: message *)`） |
| `TimerOperation::Start` | `<timer>(IN := state = <state_id>, PT := T#<ms>ms);` |
| `TimerOperation::Cancel` | 阶段 1：忽略并记录警告（自动复位策略已覆盖其语义） |

### 2.2 状态编号规则（明确版）

**规则选择**：**按 IR 原始顺序分配**，不做排序。

规则：
- 按 `StateMachine.states` 的原始顺序分配：`0, 10, 20, ...`
- 每个 state_id 递增 10，预留中间空间用于后续插入
- 保留 `9999` 作为内部错误状态

**原因**：语义分析层已保证 `states` 顺序与 `initial`/`transition` 的一致性，不再额外排序，避免 initial ID 被错误映射。

**为什么不用枚举**：IEC 61131-3 的 `ENUM` 类型在不同 PLC 厂商的支持程度不一致，`INT` 是最通用的选择，OpenPLC 和所有商业 PLC 均支持。

### 2.3 变量命名规则（修订）

| 来源 | ST 变量名规则 | 示例 |
|---|---|---|
| 状态变量 | `_state` | `_state: INT := 0` |
| 设备输出（Extend/Retract/Set） | `<device_name>` | `valve_a: BOOL` |
| 传感器输入（wait 条件左侧） | `<device_name>` | `sensor_a_ext: BOOL` |
| 模拟量 | `<device_name>` | `pressure_in: REAL` |
| 定时器实例 | `_timer_<state_id>` | `_timer_20: TON` |
| 状态常量注释 | `(* <task>.<step> = <id> *)` | `(* init.extend_a = 0 *)` |

**命名约束（必须实现）**：
- 统一小写，下划线分隔
- 非法字符替换为 `_`，连续 `_` 压缩
- 以数字开头时前置 `_`
- 与 ST 保留字冲突时前置 `_`
- 与内部变量冲突时前置 `_u_`
- 规范化后仍冲突 → 直接报错

### 2.4 定时器生成规则

每个含 `Timeout` 或 `Delay` guard 的 transition 生成一个 `TON` 实例。

**关键约束**：`TON` 的 `IN` 引脚必须在 `CASE` 块**之前**调用，否则定时器在状态切换的同一个扫描周期内不会启动。

生成顺序：
```st
(* 1. 先调用所有定时器 *)
_timer_0(IN := _state = 0,  PT := T#500ms);
_timer_10(IN := _state = 10, PT := T#500ms);

(* 2. 再执行 CASE 状态机 *)
CASE _state OF
    0: (* init.extend_a *)
        ...
END_CASE;
```

**复位策略**：`IN := _state = <id>`，状态切换后自动复位。阶段 1 忽略 Cancel。

## 3. 生成的 ST 代码结构

以 `examples/two_cylinder.plc` 为目标，完整生成结果如下（示例 ID 与“原始顺序递增”规则一致）：

```st
(* Generated by RustPLC ST Codegen *)
(* Source: examples/two_cylinder.plc *)
(* Verification: PASSED - Safety/Liveness/Timing/Causality *)
(* WARNING: Verification assumes ideal real-time execution model. *)
(*          Engineer must confirm target PLC execution environment *)
(*          is sufficiently close to this assumption.              *)

PROGRAM Main
VAR
    (* State machine *)
    _state: INT := 0;  (* initial: init.extend_a *)

    (* Timers *)
    _timer_0:  TON;
    _timer_10: TON;
    _timer_20: TON;
    _timer_30: TON;

    (* Device outputs *)
    valve_a: BOOL := FALSE;
    valve_b: BOOL := FALSE;

    (* Device inputs *)
    sensor_a_ext: BOOL := FALSE;
    sensor_a_ret: BOOL := FALSE;
    sensor_b_ext: BOOL := FALSE;
    sensor_b_ret: BOOL := FALSE;
    start_button: BOOL := FALSE;
END_VAR

(* State constants (order = StateMachine.states order):
   init.extend_a       = 0
   init.retract_a      = 10
   init.extend_b       = 20
   init.retract_b      = 30
   fault_handler.safe  = 40
   fault_handler.alarm = 50
   ready.wait_start    = 60
*)

(* Timer calls - must precede CASE block *)
_timer_0(IN  := _state = 0,    PT := T#500ms);
_timer_10(IN := _state = 10,   PT := T#500ms);
_timer_20(IN  := _state = 20,  PT := T#500ms);
_timer_30(IN := _state = 30,   PT := T#500ms);

CASE _state OF

    0: (* init.extend_a *)
        valve_a := TRUE;
        IF sensor_a_ext THEN
            _state := 10;
        ELSIF _timer_0.Q THEN
            _state := 40;  (* -> fault_handler.safe *)
        END_IF;

    10: (* init.retract_a *)
        valve_a := FALSE;
        IF sensor_a_ret THEN
            _state := 20;
        ELSIF _timer_10.Q THEN
            _state := 40;
        END_IF;

    20: (* init.extend_b *)
        valve_b := TRUE;
        IF sensor_b_ext THEN
            _state := 30;
        ELSIF _timer_20.Q THEN
            _state := 40;
        END_IF;

    30: (* init.retract_b *)
        valve_b := FALSE;
        IF sensor_b_ret THEN
            _state := 60;  (* on_complete: goto ready *)
        ELSIF _timer_30.Q THEN
            _state := 40;
        END_IF;

    40: (* fault_handler.safe *)
        valve_a := FALSE;
        valve_b := FALSE;
        _state := 50;

    50: (* fault_handler.alarm *)
        (* LOG: 动作超时报警 *)
        _state := 60;  (* on_complete: goto ready *)

    60: (* ready.wait_start *)
        IF start_button THEN
            _state := 0;  (* on_complete: goto init *)
        END_IF;

END_CASE;

END_PROGRAM
```

## 4. 新增模块设计

### 4.1 模块位置

新建 `src/codegen/st.rs`，不放在 `crates/codegen`。

**原因**：`crates/codegen` 的输入是 `runtime_core::Program`（已经过 runtime_bridge 降级的低层 IR），而 ST 生成需要的是 `StateMachine` + `TopologyGraph`（语义分析输出的高层 IR）。两者输入不同，不应共用同一个 crate。`crates/codegen` 继续服务于 RP2040/runtime-core 路径，`src/codegen/st.rs` 服务于 ST 生成路径。

### 4.2 公开接口（修订）

```rust
// src/codegen/st.rs

pub struct StCodegenConfig {
    /// 程序名，默认 "Main"
    pub program_name: String,
    /// 源文件路径，用于生成注释头
    pub source_file: String,
    /// 是否在注释中包含验证结果摘要
    pub include_verification_summary: bool,
}

impl Default for StCodegenConfig {
    fn default() -> Self {
        Self {
            program_name: "Main".to_string(),
            source_file: String::new(),
            include_verification_summary: true,
        }
    }
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum StCodegenError {
    /// 程序包含 parallel 块，阶段 1 不支持
    ParallelNotSupported { task: String, step: String },
    /// 程序包含 race 块，阶段 1 不支持
    RaceNotSupported { task: String, step: String },
    /// StateMachine 为空（无 states）
    EmptyStateMachine,
    /// goto 目标不存在
    UnresolvedGoto { from: String, target: String },
    /// 变量名规范化后发生冲突
    VariableNameConflict { original: String, normalized: String },
    /// 变量类型冲突（BOOL vs REAL）
    TypeConflict { name: String },
    /// 条件表达式无法解析
    ExpressionNotSupported { expr: String },
}

/// 从语义分析输出的 IR 生成 IEC 61131-3 ST 代码。
///
/// 阶段 1 限制：不支持 parallel/race/复杂表达式。
pub fn generate_st(
    topology: &TopologyGraph,
    state_machine: &StateMachine,
    config: &StCodegenConfig,
) -> Result<String, Vec<StCodegenError>>
```

### 4.3 内部结构

```
generate_st
  ├── check_unsupported_constructs   // 检查 parallel/race/复杂表达式
  ├── assign_state_ids               // 依据 StateMachine.states 原始顺序
  ├── normalize_variable_names       // 变量名规范化与冲突检测
  ├── collect_variables              // 从 topology + transitions 收集所有变量
  ├── collect_timers                 // 从 transitions 收集所有 TON 实例
  ├── emit_header                    // 生成注释头（来源、验证结果、假设边界声明）
  ├── emit_var_block                 // 生成 VAR...END_VAR
  ├── emit_state_constants_comment   // 生成状态常量注释
  ├── emit_timer_calls               // 生成 CASE 块前的定时器调用
  └── emit_case_block                // 生成 CASE _state OF ... END_CASE
        └── emit_state_branch        // 为每个 state 生成一个 CASE 分支
              ├── emit_actions       // 生成动作赋值
              └── emit_guard         // 生成 IF 条件跳转/Always 跳转
```

## 5. 变量收集规则

### 5.1 输出变量（BOOL，来自 actions）

遍历所有 `Transition.actions`：
- `Extend { target }` → `<target.device>: BOOL := FALSE`
- `Retract { target }` → `<target.device>: BOOL := FALSE`
- `Set { target, .. }` → `<target.device>: BOOL := FALSE`

去重（同一设备名只声明一次）。

### 5.2 输入变量（BOOL/REAL，来自 wait 条件）

遍历所有 `Transition.guard: Condition { expression }`，解析 expression 字符串中的设备名：
- 布尔条件（`sensor_a_ext == true`）→ `sensor_a_ext: BOOL := FALSE`
- 模拟量条件（`pressure_in > 5.0`）→ `pressure_in: REAL := 0.0`

**硬性规则**：只支持 `<name> == <value>`、`<name> != <value>`、`<name> > <value>`、`<name> < <value>` 四类简单形式。其他表达式一律报 `ExpressionNotSupported`。

### 5.3 模拟量变量（REAL，来自 SetAnalog/SetAnalogExpr）

- `SetAnalog { target, .. }` → `<target.device>: REAL := 0.0`
- `SetAnalogExpr { target, .. }` → `<target.device>: REAL := 0.0`

### 5.4 变量类型推断优先级（修订）

同一变量名可能在不同 action 中出现。类型推断规则：
1. 出现在 `SetAnalog`/`SetAnalogExpr` 中 → `REAL`
2. 出现在 `Extend`/`Retract`/`Set` 中 → `BOOL`
3. 出现在模拟量 wait 条件中 → `REAL`
4. 出现在布尔 wait 条件中 → `BOOL`
5. 冲突（同一变量既是 BOOL 又是 REAL）→ 直接报错 `TypeConflict`

## 6. 阶段 1 的已知限制

| 限制 | 原因 | 解除条件 |
|---|---|---|
| 不支持 `parallel`/`race` 块 | 分支同步语义（all-complete / first-complete）需要为每个分支维护独立完成标志变量 | 阶段 3 专项处理 |
| expression 字符串只支持简单形式 | expression 是字符串，需解析 | 阶段 2 改为结构化 expression IR |
| 不生成 I/O 地址注释 | 物理地址映射规则未定义 | 阶段 3（基恩士适配）时处理 |
| 不生成变量表配置文件 | 针对 OpenPLC，不需要外部变量表 | 阶段 3（基恩士适配）时生成 |
| `Log` 动作生成为注释 | ST 无标准日志原语 | 可选：阶段 3 映射为厂商特定功能块 |
| 多任务程序生成单个 `CASE` 块 | 简化实现 | 阶段 3 可选：按任务生成多个 FB |

## 7. 阶段 2：端到端验证闭环

### 7.1 目标

建立 `.plc → ST 生成 → OpenPLC 编译 → 执行 → trace 对比` 的可持续自动化回归链路。

### 7.2 OpenPLC 编译验证

OpenPLC 内置 MATIEC 编译器（来自 Beremiz 项目）。ST 代码的完整编译链为：

```
ST 源码 → MATIEC（iec2c）→ C 代码 → GCC → 可执行文件
```

CI 中直接调用 MATIEC 验证 ST 语法与语义：

```bash
# 安装 MATIEC（Ubuntu）
sudo apt-get install matiec

# 编译验证（具体参数需对照 MATIEC 实际文档确认）
iec2c output.st
```

`iec2c` 返回非零退出码表示编译失败，CI 可直接用退出码判断。

阶段 2 的 CI 步骤：

```bash
cargo run -- gen-st examples/two_cylinder.plc --out /tmp/two_cylinder.st
iec2c /tmp/two_cylinder.st
```

> **待确认**：MATIEC 的具体命令行参数需在阶段 2 实施时对照实际安装版本的文档验证。

### 7.3 trace 对比规范（修订）

**SIL trace**（已有）：`cargo run --bin sim -- examples/two_cylinder.plc scenarios/two_cylinder.yaml`，输出 `sil_trace.jsonl`。

**OpenPLC trace**（新增）：**必须先定义变量到地址的映射规则**，否则无法采集。阶段 2 推荐以下两条路径之一：
1. 通过 OpenPLC 运行时 API/日志接口导出变量快照（若可用）。
2. 通过 Modbus TCP 读取变量值，但需明确变量映射规则（地址表/导出文件）。

**对比规则**：
- 每个 tick 的状态变量值必须一致（`_state` 值相同）
- 输出变量（`valve_a`、`valve_b`）值必须一致
- 允许的差异：OpenPLC 的扫描周期与 SIL 仿真的 tick_ms 不完全对齐，允许 ±1 tick 的时序偏差

**阶段 2 验收标准**：核心场景（`two_cylinder.plc` + `assembly_station.plc`）的 trace 对比通过率 ≥ 95%。

### 7.4 回归测试集定义

阶段 2 新增的测试：

| 测试名 | 内容 | 验收条件 |

| `st_codegen_two_cylinder_compiles` | `two_cylinder.plc` 生成 ST，OpenPLC 编译通过 | 编译无错误 |

| `st_codegen_expression_rejected` | 复杂表达式被拒绝 | 错误类型正确 |

## 9. 验收测试矩阵

### 阶段 1 验收

| 测试项 | 验证内容 | 测试方式 |

## 10. 设计决策记录

| 决策 | 选项 | 选择 | 理由 |
|---|---|---|---|
| ST 生成器位置 | `crates/codegen` vs `src/codegen/st.rs` | `src/codegen/st.rs` | 输入 IR 不同，不应共用 crate |
| 状态变量类型 | `INT` vs `ENUM` | `INT` | ENUM 在各厂商支持不一致，INT 最通用 |
| 状态 ID 分配 | 原始顺序 vs 排序后重排 | 原始顺序 | 避免 initial/transition 映射错误 |
| 定时器调用位置 | CASE 块内 vs CASE 块前 | CASE 块前 | 确保定时器在状态激活的第一个扫描周期即开始计时 |
| 定时器复位方式 | 手动 `IN := FALSE` vs 状态条件自动复位 | 状态条件自动复位（`IN := _state = <id>`） | 更简单，无需手动管理，符合 IEC 61131-3 惯用法 |
| `parallel`/`race` 处理 | 阶段 1 支持 vs 阶段 1 排除 | 阶段 1 排除 | 分支同步语义需要独立完成标志变量，阶段 1 先打通顺序逻辑核心链路 |
| 多任务结构 | 单 PROGRAM vs 多 FB | 单 PROGRAM | 阶段 1 简化实现，阶段 3 可选重构 |
| `Log` 动作 | 生成注释 vs 生成厂商功能块 | 生成注释 | 无标准 ST 日志原语，注释最通用 |
| Timer Cancel | 报错 vs 忽略 | 忽略并告警 | 与自动复位策略冲突，阶段 1 先保证可用 |
| 变量名规范化 | 宽松通过 vs 强制规范化 | 强制规范化 | 避免生成非法 ST 代码 |
