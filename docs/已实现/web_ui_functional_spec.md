# RustPLC Web 界面功能规格（风格无关）

日期：2026-02-19

## 1. 文档目的

这份文档只定义“界面必须具备什么功能”，不限制视觉风格（颜色、布局、组件库都不做约束）。
目标是让前端团队、后端团队、评审人员对功能范围有统一理解。

---

## 2. 设计原则（功能层）

1. **安全优先**：所有可能影响设备动作的操作都必须有防误触机制。
2. **可追溯**：关键操作、配置变更、告警确认都要有审计记录。
3. **可评审**：拓扑、约束、场景、运行结果都要可回放与可签核。
4. **有/无板统一**：无板（no-board）与有板（HIL/live）用同一套页面模型，仅数据源不同。
5. **契约优先**：优先消费现有后端工件（`commissioning_index.json`、`diagnosis_report.json`、`alarm_event` 等）。

---

## 3. 用户角色与权限

至少支持以下角色（可映射到现有账号体系）：

- **操作员**：查看状态、执行受限操作、确认告警。
- **调试工程师**：运行调试流程、查看诊断、申请临时强制写入。
- **工艺/安全审核员**：审批拓扑与约束变更、签字放行。
- **管理员**：用户权限、系统参数、审计导出。

权限原则：

- 读写分离（查看 ≠ 修改）。
- “可致动风险操作”需更高权限 + 二次确认。
- 审核动作需与执行动作分离（不能自己提自己批）。

---

## 4. 页面与功能清单（必须项）

## 4.1 总览看板（Dashboard）

必须展示：

- 当前项目/产线/配方（或场景）
- 运行模式：`no_board` / `hil_board` / `runtime_live`
- 最新运行状态（运行中/空闲/失败）
- 最新告警数量（按严重级别）
- 最近一次 gate 结果（pass/fail）
- 快速入口（运行、回放、诊断、审核）

## 4.2 拓扑与约束评审页（Topology & Constraints Review）

必须支持：

- 拓扑图查看（设备、连接、信号方向）
- 元器件库拖拽建模（至少含：气缸、传感器、开关、步进电机/电缸）
- 元器件库检索与分类（按类型/标签/关键词过滤）
- 元器件参数面板（参数编辑、单位提示、默认值回填）
- 约束查看（requires/conflicts、互斥、角度区间限制）
- 变更对比（当前版本 vs 上一批准版本）
- 评审结论：通过/驳回 + 评论
- 电子签核（签名人、时间、理由）

必须支持拓扑编辑保存语义：

- 从“元器件库”拖入拓扑画布后，形成拓扑节点与连接关系。
- 拓扑改动后，保存动作必须落盘到拓扑文件（项目内配置文件）。
- 有未保存改动时，页面必须有**明显提示**（如标题标记、离开拦截、保存按钮高亮）。
- 未保存状态下禁止进入“提交评审/放行”动作。
- 连接线编辑时需即时校验：端口类型不匹配、方向错误、关键输入悬空必须即时提示。

必须有状态流转：

`Draft -> In Review -> Approved -> Locked`

`Locked` 后禁止直接改动，必须“新建版本”。

## 4.3 场景/配方页（Scenario/Recipe）

必须支持：

- 场景文件选择与版本切换
- 场景参数查看与编辑（tick、duration、输入事件、故障注入）
- 调用校验结果展示（含错误码）
- 可视化时间轴（输入/故障在何时发生）

## 4.4 运行与门禁页（Run & Gate）

必须支持一键触发并展示：

- `sim-plc`
- `no-board-gate`
- `commissioning-run`
- `trace-doctor`

必须展示每次运行的：

- Run ID、触发人、触发时间
- 状态（running/pass/fail）
- 工件链接（trace、diff、timing、diagnosis、index）
- 失败原因摘要（可点击展开详情）

## 4.5 Tick 回放审查页（Tick Replay Inspector）

必须支持：

- 按 tick 浏览状态
- 可拖动 tick 时间轴（slider/scrubber）
- 同步查看 DI/AI/DO/AO 在该 tick 的值
- 查看该 tick 发生的动作与状态迁移
- 对比“预期 vs 实际”（至少支持 trace/diff 对照）
- 支持跳转到首个异常锚点（timeout/mismatch）

必须支持“关键点跳转”：

- 系统根据程序与场景给出关键时刻列表（如“预计 20ms 传感器置位”“预计 50ms 告警触发”）。
- 用户可通过按钮一键跳转到关键 tick（不仅是手动拖动）。
- 跳转后，画布元器件状态必须同步刷新到该 tick 的快照。
- 支持“上一个关键点/下一个关键点”快捷键跳转。

必须支持“元器件状态联动回放”：

- 传感器在该 tick 的状态（ON/OFF 或数值）实时反映。
- 气缸类元件状态根据执行器输出变化联动（伸出/回缩/中间态）。
- 电机类元件状态可显示方向、使能、位置/角度（如果有该数据）。
- 支持“同一 tick 多源证据联动”：拓扑高亮、IO 值、诊断证据、告警事件同步定位。

## 4.6 离线交互仿真画布（Offline Interactive Simulation）

必须支持（no-board 调试态）：

- 在画布上直接点击传感器，注入一次手动输入（等价于临时输入事件）。
- 支持“按下/释放”两类交互，自动转换为 DI 变化事件并记录时间戳。
- 交互注入后可立即在 tick 回放中看到状态变化。
- 手动注入必须写入审计（谁在何时注入了什么输入）。
- 支持执行器异常注入（例如：气缸被阻挡/不动作、执行器输出被钳制、动作延迟）。
- 支持“注入草稿”与“一次性注入”两种模式（先编辑后执行，或即点即生效）。
- 支持按组件实例 ID 选择注入目标（与拓扑实例一致）。

必须有“故障注入能力标识”：

- 对每种注入项显示能力状态：`已原生支持` / `可近似模拟` / `待后端实现`。
- 当后端不支持原生模型时，UI 仍可给出近似注入方式（例如 force + 传感器卡滞组合），并明确提示“这是近似模拟，不是物理精确故障”。

当前后端能力现状（用于前端设计边界）：

- 已原生支持（组件级注入，`component_faults`）：
  - 气缸：`jammed`、`motion_timeout`
  - 传感器：`stuck_on`、`stuck_off`、`chatter`
  - 开关：`stuck_on`、`stuck_off`
  - 步进：`lost_step`、`stall`、`direction_reversed`
- 已支持运行产物：
  - 组件 trace（每 tick 元件状态）
  - fault 审计（激活/失效）
  - 组件诊断（含 fault_injection / program_behavior 证据分类）

说明：离线交互注入仅用于调试，不等于真实硬件输入，不应绕过安全评审流程。

## 4.7 寄存器/强制控制页（Override & Register Control）

必须支持（仅授权角色可用）：

- 鼠标强制写入 DI/AI/DO/AO（或抽象变量）
- 设置持续时间（TTL），到期自动恢复
- 清除强制状态
- 批量操作预览（执行前显示将改动哪些点）
- 在线变量写入（变量名/目标值/生效 tick/审计）

必须有安全保护：

- 二次确认（含风险提示）
- 与互锁/互斥约束冲突时阻止提交
- 关键通道白名单机制（默认不可改）
- 完整审计记录（谁、何时、改了什么、为何改）
- 必须区分“开发态允许”与“生产态禁止”能力，并在界面显著展示。

## 4.8 告警与诊断中心（Alarm & Diagnosis）

必须支持：

- 实时告警流（来自 `alarm_event`）
- 告警去重展示（同类告警聚合）
- 告警确认/关闭（Ack/Close）
- Top-N 候选原因展示（`issue_code`、`confidence`、`evidence`）
- 证据来源标记（`evidence_source`）
- 证据工件跳转（`evidence_ref`、`diagnosis_report.json`）
- 告警与诊断推送到 HMI（实时通道失败时自动回退到轮询）

必须让非专业人员也能读懂：

- 每个 `DIAG-*` 码有“人话解释”
- 给出下一步建议（如检查传感器接线、检查映射、放宽超时）
- 必须展示“可能原因置信度不是结论”的提示，避免误操作。

## 4.9 审计与报告页（Audit & Reports）

必须支持：

- 审计事件筛选（时间、人、对象、操作类型）
- 关键记录不可篡改（至少只读呈现 + 导出）
- 导出报告（JSON/CSV/PDF 至少一种结构化导出）
- 可追溯链路：从一次告警跳回对应运行、工件、配置版本

## 5. 关键业务流程（必须闭环）

### 流程 A：拓扑变更评审到放行

1. 工程师提交拓扑新版本（Draft）
2. 审核员查看变更差异 + 约束冲突检查
3. 审核员签核通过（Approved）
4. 系统锁定该版本（Locked）并允许进入运行流程

### 流程 B：运行失败后的诊断闭环

1. 运行失败（no-board/hil/live 任一）
2. UI 自动关联诊断工件并展示 Top-N 原因
3. 用户定位证据（tick 回放、trace/diff/timing）
4. 用户记录处理结论并关闭告警

### 流程 C：临时强制干预闭环

1. 授权用户发起强制写入
2. 系统执行安全检查（权限、约束冲突、白名单）
3. 执行并记录审计
4. 到期自动恢复或手动解除

### 流程 D：离线交互 + 关键点快进闭环

1. 工程师在 no-board 模式拖动或跳转到关键 tick
2. 工程师点击传感器注入输入，观察执行器/气缸联动
3. 工程师按需注入执行器异常（如“气缸阻挡”近似场景）
4. 系统记录输入注入、故障注入与状态变化审计
5. 工程师确认行为符合预期后再进入正式 gate

---

## 6. 数据与接口契约（前端必须对齐）

前端必须直接支持以下关键工件/消息：

- `commissioning_index.json`（步骤状态与工件索引）
- `diagnosis_report.json`（候选原因与证据）
- `no-board-gate --output json`（含 `diagnosis_report` 等字段）
- `trace-doctor --output json`（含 `evidence_source`、`evidence_inputs`）
- `alarm_event`（实时通道，如 WebSocket）
- `component-topology-validate --output json`（拓扑结构合法性、稳定错误码）
- `component-scenario-validate --output json`（场景合法性、迁移错误码）
- `component-sim --output json`（运行摘要）
- `component_trace.jsonl`（组件级 tick 回放数据）
- `fault_audit.jsonl`（注入异常生命周期审计）
- `component_diagnosis.json`（组件异常上下文诊断）
- 拓扑文件读写（用于元器件拖拽建模后的持久化）
- tick 关键点列表（可由后端推导后返回，供一键跳转）
- scenario 组件注入字段（`switch_events`、`sensor_events`、`component_faults`）

前端不应自行发明与后端冲突的诊断字段。

---

## 7. 统一“有板/无板”模式要求

同一页面必须可切换模式：

- **No-board 模式**：重点看 trace/diff/timing/diagnosis 工件
- **Board/Live 模式**：重点看实时告警、实时状态、同样的诊断编码

切换模式只改变数据源，不改变用户操作心智。

---

## 8. 安全与审计硬要求

1. 所有写操作必须带操作者身份。
2. 所有高风险操作必须有确认弹窗 + 风险说明。
3. 告警确认与放行审批必须可追溯到人和时间。
4. 关键审计记录不可由普通角色删除。
5. 页面需明确显示当前是否为开发态能力（例如在线强制控制）。

---

## 9. 非功能要求（仅与功能可靠性有关）

- 页面刷新或重连后，状态恢复一致（不丢关键上下文）。
- 同一份工件重复加载，展示结果一致（确定性）。
- 实时告警展示支持限流，避免前端被告警风暴拖垮。
- 后端实时通道异常时，前端可退化到审计文件/轮询读取。

---

## 10. 明确不在本规格内的内容

- 不规定 UI 主题、色板、动效、组件库。
- 不规定桌面端/移动端具体适配细节。
- 不规定品牌视觉规范。

本规格只定义“必须实现的功能能力”和“必须可审计的行为”。

---

## 11. 执行器异常注入（实现建议）

为了支持“挡住气缸”这类场景，建议 UI 按以下模型落地：

### 当前可做（基于组件模型）

- 直接使用 `component_faults` 注入 `jammed`，表达“命令发出但机构不动”。
- 需要固定反馈时，叠加传感器 `stuck_on/stuck_off`。
- UI 上显示“逻辑级故障模型”，并说明与真实物理受力模型的差异。

### 后续增强（可选）

- 新增更细化故障类型（示例：`actuator_slow`、`actuator_backlash`）。
- UI 可从故障面板直接配置故障起始时间、持续时间、影响对象、严重级别。
- 诊断输出可直接关联执行器故障类型，减少“由症状反推”的歧义。

---

## 12. 给视觉团队的固定信息架构（不含风格）

前端视觉同学可在不改变功能语义的前提下自由设计，但以下信息架构建议固定：

1. 顶层导航：`总览` / `拓扑` / `场景` / `运行` / `回放` / `诊断` / `审计`
2. 右上角常驻状态：模式（no-board/hil/live）、当前版本、未保存状态、当前用户角色
3. 页面通用“工件抽屉”：任何页面可快速打开 trace/diagnosis/audit 链接
4. 统一风险条：高风险操作（强制写入、上线放行）统一使用同一风险提示与二次确认结构

这样可以让后续视觉换肤、组件替换、布局调整不影响核心流程与审计要求。
