# 异常退出后的 Safe State 设计说明（RustPLC）

日期：2026-02-18

---

## 1. 先回答核心问题

**本文采用直接结论：默认“输出置 0”，例外点位走配置化 Safe Profile。**

工程口径如下：

- 异常退出后，系统应进入**预定义安全态（Safe State）**
- 大多数点位使用“**输出置 0（de-energize）**”
- 垂直电缸/特殊机构等少数点位使用 `profile` 明确 `safe_value` 与执行顺序
- 安全责任分层：机械/电气安全链是主安全，软件负责可控停机与审计

例如：

- 垂直轴：若无抱闸，或抱闸极性配置错误，`EN=0` 可能导致下滑
- 气缸：线圈断电后是回缩还是保持，要看阀型与机构风险
- 加热器：通常断电为安全态

---

## 2. 适用范围

本文用于定义 RustPLC 在以下场景的安全策略：

- 程序异常退出（含可控停止、崩溃、被强制终止）
- 运行时被停止（服务退出、人工停止）
- 通信中断/控制器故障后的输出处理策略

本文不替代硬件安全设计（急停、安全继电器、STO、抱闸等），仅定义软件层行为与接口约定。

---

## 3. 先定义：什么叫“异常退出”

工程上建议把“异常退出”分为四类（按可控程度）：

| 类别 | 示例 | 软件是否有机会执行停机逻辑 | 结论 |
|---|---|---|---|
| A. 可控停止 | UI Stop、服务 SIGTERM、程序主动退出 | 通常有 | 可依赖软件写 Safe State |
| B. 可恢复异常 | 协议线程故障、模块异常被捕获 | 有 | 应优先走 fault/降级顺控 |
| C. 进程级崩溃 | 段错误、abort、未捕获 panic | 不确定 | 只能“尽力而为”，不可强依赖 |
| D. 不可控终止 | `kill -9`、掉电、内核死机 | 没有 | 只能依赖硬件安全链 |

> 关键结论：  
> - 软件 Safe State 对 A/B 可靠，对 C 可能有效，对 D 无效。  
> - 因此必须同时具备硬件安全链。

---

## 4. 基本原则

1. **Safe State 优先于“归零”**
2. **硬件安全链优先于软件安全链**
3. **先止险，再复位**
4. **状态可审计**（配置可查、行为可回放、结果可验证）

---

## 5. 两层安全架构（必须同时存在）

### 5.1 硬件层（主安全）

硬件层负责“控制器死机也安全”：

- 急停回路（E-Stop）
- 安全继电器/安全接触器
- 驱动器 STO
- 机械抱闸
- 气源/真空的安全泄放路径

### 5.2 软件层（辅助安全）

软件层负责“可控停机 + 可审计策略”：

- 触发停机时写入配置化 Safe State
- 记录日志与事件
- 输出执行结果（成功/超时/失败）

---

## 6. 执行器 Safe State 参考表

| 执行器类型 | 典型风险 | 常见 Safe State（示例） | 备注 |
|---|---|---|---|
| 步进/伺服水平轴 | 继续运动碰撞 | `STEP=0`, 取消运动命令, `EN=0` 或 STO | 需与驱动逻辑一致 |
| 步进/伺服垂直轴 | 重力下滑 | **先让抱闸进入制动态（多数常闭刹车为 `brake=0`），再禁能=0** | 必须按电气图确认抱闸极性 |
| 双作用气缸 | 夹伤/顶撞 | 阀切到“回缩安全位”或“中位锁定” | 取决于阀芯类型 |
| 真空吸附 | 掉件 | 先降速/托举，再破真空 | 与工艺相关 |
| 加热器 | 过温 | 加热输出=0 | 通常可直接断开 |
| 刀具/主轴 | 旋转伤害 | 使能=0 + 制动 | 关注惯性停机时间 |

> 上表是模板，不是默认值。项目必须做风险评估后落配置。

## 7. “中途归零是否安全”的判定方法

对每个输出点做以下判定：

1. 写 0 后执行器会到哪个机械状态？
2. 该状态在“当前工位任意时刻”是否都安全？
3. 若不安全，是否需要有序动作（A 后 B）？
4. 若进程已崩溃，硬件链能否独立保证安全？

只要出现“不确定/有风险”点位，就切换为 `profile` 策略，按点位定义 `safe_value` 与 `group`。

---

## 8. 异常退出是不是“正常现象”？

异常退出属于**低频故障场景**，工程上按“必须覆盖”处理。

现场常见诱因包括：

- 程序 bug（越界、空指针、未处理异常）
- 资源耗尽（内存、文件句柄、磁盘）
- 通信库/驱动异常
- 人工运维操作（误杀、重启、升级）
- 系统级问题（内核/驱动异常、掉电）

工程态度应是：

- 把异常退出当作**低频但必须覆盖**的故障场景；
- 通过“软件 Safe State + 硬件安全链”做防御式设计。

---

## 9. 参考：OpenPLC_v3 的做法（为什么它能“简单置 0”）

OpenPLC_v3 在正常退出流程中会调用 `disableOutputs()`，将数字/字节/模拟输出缓冲统一清零并写回输出镜像。

这种策略成立的前提是：系统的硬件/机构按“**断电安全（de-energize-to-safe）**”理念设计，即“输出断电 = 进入安全态”。

注意点（对 RustPLC 的启发）：

- OpenPLC 的 `disableOutputs()` 作用在“程序主循环正常退出”的收尾阶段。
- 对进程级崩溃/掉电等不可控终止，系统依赖硬件安全链（急停、安全继电器、STO、抱闸等）。

---

## 10. 程序崩溃后 IO 状态由什么决定？

崩溃后的 IO 状态由“崩溃形态 + 硬件/驱动实现”共同决定：

- 进程崩溃但系统不复位：GPIO/IO 模块常常保持“上一次输出状态”（或变为高阻/输入，但被上拉导致仍为高）
- `kill -9`：用户态清理逻辑不会执行
- 掉电/系统死机：只能靠硬件安全链
- 设备复位/看门狗触发复位/IO 模块掉线看门狗生效时，IO 会回到默认态（通常为断电/输入态）

落地要求：若目标是“崩溃后进入断电安全态”，关键输出需满足：

- 信号丢失/高阻/断电都会回到安全态（下拉/失电复位/常闭阀/弹簧复位/安全继电器等）
- IO 模块或驱动器具备掉线看门狗/安全功能（STO/抱闸）

## 11. RustPLC 推荐落地方式

### 11.1 配置层（建议）

在 `io_map`（或等价运行时配置）中为输出定义安全策略。示例（提案格式，尚未实现）：

```toml
[safe_state]
mode = "all_zero"  # all_zero | profile
on_exit_timeout_ms = 300

# 当 mode = "profile" 时，才读取下面每个点位的 safe_value/group
[safe_state.do.Y0] # step_dir
safe_value = 0
group = 20

[safe_state.do.Y1] # step_en
safe_value = 0
group = 30

[safe_state.do.Y2] # brake_coil (NC brake, 0=brake)
safe_value = 0
group = 10

[safe_state.ao.AO0] # heater
safe_value = 0.0
group = 20
```

含义：

- `all_zero`：简单策略。对绝大多数“断电安全”机构足够（推荐默认）
- `profile`：带例外的策略。用于少数需要非 0 安全值或有序停机的点位
- `safe_value` 按点位极性逐点配置（例如常闭刹车常见 `0=抱闸`）
- `group` 越小越先执行（用于“先抱闸再禁能”等有序停机）
- 同组并行写入
- `on_exit_timeout_ms` 控制最大停机动作窗口

### 11.2 运行时行为（建议）

1. 接收到停机事件后，冻结新动作下发
2. 按 `group` 顺序写 Safe State
3. 超时后记录告警并退出
4. 输出事件日志（含每个点位最终值）

## 12. 验证与测试要求

### 12.1 SIL 测试

- 正常停机：检查 Safe State 顺序与最终值
- panic 注入：检查是否触发停机流程
- 超时场景：检查告警与退出行为

### 12.2 HIL 测试

- 验证关键点（抱闸、禁能、阀位）电气状态
- 验证“最坏时刻停机”时机构是否仍安全
- 验证硬件急停链独立生效

---

## 13. 项目评审清单（上线前必答）

1. 每个输出点是否有明确 Safe State？
2. 是否存在“写 0 不安全”的点？已单独处理？
3. 是否需要有序停机（group）？
4. `kill -9`/掉电时硬件链能否独立保证安全？
5. SIL/HIL 是否覆盖最坏时刻停机？

---

## 14. 与当前 RustPLC 范围的关系

当前阶段建议先做：

1. 配置化 `safe_value`（先覆盖 DO/AO）
2. 异常退出写入 Safe State
3. 基础回归测试（SIL）

后续再扩展：

- 分组有序停机
- 更细粒度故障类型策略
- 与外部安全 PLC/继电器的状态握手
