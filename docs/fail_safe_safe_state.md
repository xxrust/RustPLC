# 异常退出后的 Safe State 设计说明（RustPLC）

日期：2026-02-18

---

## 1. 先回答核心问题

**“异常退出后输出归零”并不总是安全。**

正确说法应是：

- 异常退出后，系统应进入**预定义安全态（Safe State）**
- Safe State 对不同执行器不同，**不等于统一写 0**

例如：

- 垂直轴：`EN=0` 可能导致掉落，不一定安全
- 气缸：线圈断电后是回缩还是保持，要看阀型与机构风险
- 加热器：通常断电为安全态

---

## 2. 适用范围

本文用于定义 RustPLC 在以下场景的安全策略：

- 程序异常退出（panic、进程崩溃）
- 运行时被停止（服务退出、人工停止）
- 通信中断/控制器故障后的输出处理策略

本文不替代硬件安全设计（急停、安全继电器、STO、抱闸等），仅定义软件层行为与接口约定。

---

## 3. 基本原则

1. **Safe State 优先于“归零”**
2. **硬件安全链优先于软件安全链**
3. **先止险，再复位**
4. **状态可审计**（配置可查、行为可回放、结果可验证）

---

## 4. 两层安全架构（必须同时存在）

### 4.1 硬件层（主安全）

硬件层负责“控制器死机也安全”：

- 急停回路（E-Stop）
- 安全继电器/安全接触器
- 驱动器 STO
- 机械抱闸
- 气源/真空的安全泄放路径

### 4.2 软件层（辅助安全）

软件层负责“可控停机 + 可审计策略”：

- 触发停机时写入配置化 Safe State
- 记录日志与事件
- 输出执行结果（成功/超时/失败）

---

## 5. 执行器 Safe State 参考表

| 执行器类型 | 典型风险 | 常见 Safe State（示例） | 备注 |
|---|---|---|---|
| 步进/伺服水平轴 | 继续运动碰撞 | `STEP=0`, 取消运动命令, `EN=0` 或 STO | 需与驱动逻辑一致 |
| 步进/伺服垂直轴 | 重力下滑 | **先抱闸=1，再禁能=0** | 严禁直接套用“全 0” |
| 双作用气缸 | 夹伤/顶撞 | 阀切到“回缩安全位”或“中位锁定” | 取决于阀芯类型 |
| 真空吸附 | 掉件 | 先降速/托举，再破真空 | 与工艺相关 |
| 加热器 | 过温 | 加热输出=0 | 通常可直接断开 |
| 刀具/主轴 | 旋转伤害 | 使能=0 + 制动 | 关注惯性停机时间 |

> 上表是模板，不是默认值。项目必须做风险评估后落配置。

---

## 6. “中途归零是否安全”的判定方法

对每个输出点做以下判定：

1. 写 0 后执行器会到哪个机械状态？
2. 该状态在“当前工位任意时刻”是否都安全？
3. 若不安全，是否需要有序动作（A 后 B）？
4. 若进程已崩溃，硬件链能否独立保证安全？

只要任一输出点答复为“不确定/不安全”，就不能采用“统一归零”策略。

---

## 7. 异常类型与可执行能力

| 场景 | 是否还能执行软件停机动作 | 主要依赖 |
|---|---|---|
| 正常停止（SIGTERM/服务停止） | 通常可以 | 软件+硬件 |
| 运行时 panic | 可能可以（取决于崩溃位置） | 软件+硬件 |
| `kill -9` | 不可以 | **硬件** |
| 掉电/系统死机 | 不可以 | **硬件** |

结论：软件 Safe State 必须有，但不能替代硬件安全链。

## 8. RustPLC 推荐落地方式

## 8.1 配置层（建议）

在 `io_map`（或等价运行时配置）中为输出定义安全策略。示例（提案格式，尚未实现）：

```toml
[safe_state]
mode = "profile"  # profile | all_zero
on_exit_timeout_ms = 300

[safe_state.do.Y0] # step_dir
safe_value = 0
group = 20

[safe_state.do.Y1] # step_en
safe_value = 0
group = 30

[safe_state.do.Y2] # brake
safe_value = 1
group = 10

[safe_state.ao.AO0] # heater
safe_value = 0.0
group = 20
```

含义：

- `group` 越小越先执行（用于“先抱闸再禁能”）
- 同组并行写入
- `on_exit_timeout_ms` 控制最大停机动作窗口

## 8.2 运行时行为（建议）

1. 接收到停机事件后，冻结新动作下发
2. 按 `group` 顺序写 Safe State
3. 超时后记录告警并退出
4. 输出事件日志（含每个点位最终值）

---

## 9. 验证与测试要求

### 9.1 SIL 测试

- 正常停机：检查 Safe State 顺序与最终值
- panic 注入：检查是否触发停机流程
- 超时场景：检查告警与退出行为

### 9.2 HIL 测试

- 验证关键点（抱闸、禁能、阀位）电气状态
- 验证“最坏时刻停机”时机构是否仍安全
- 验证硬件急停链独立生效

---

## 10. 项目评审清单（上线前必答）

1. 每个输出点是否有明确 Safe State？
2. 是否存在“写 0 不安全”的点？已单独处理？
3. 是否需要有序停机（group）？
4. `kill -9`/掉电时硬件链能否独立保证安全？
5. SIL/HIL 是否覆盖最坏时刻停机？

---

## 11. 与当前 RustPLC 范围的关系

当前阶段建议先做：

1. 配置化 `safe_value`（先覆盖 DO/AO）
2. 异常退出写入 Safe State
3. 基础回归测试（SIL）

后续再扩展：

- 分组有序停机
- 更细粒度故障类型策略
- 与外部安全 PLC/继电器的状态握手
