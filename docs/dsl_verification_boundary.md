# DSL 形式化验证边界与数据类型论证（建议稿）

## 0. 目标与结论摘要
本文件回答三个问题：
1) 从数学上看，扩展 DSL 是否能实现“完整验证”？
2) 混合架构中 DSL 的边界应在哪里？
3) 数组、结构体等数据类型应如何取舍以保持可验证性？

**结论摘要**
- “完整验证”在通用计算场景不可实现，只能在严格受限子集里做到可判定的安全性与部分正确性验证。
- DSL 应定位为“控制平面”：状态机、互锁、时序与安全性约束；复杂计算进入外部函数（Rust）。
- 数组可以进入 DSL，但必须是编译期固定长度、可静态证明索引范围的受限数组。
- 结构体可以进入 DSL，但必须是“无指针、无动态分配、固定布局、字段类型可验证”的 POD 结构体。

---

## 1. 数学上“完整验证”的可行性
### 1.1 可判定性层面
当 DSL 支持以下特性之一时，通常就已经接近通用计算能力：
- 运行时循环（取决于输入）
- 递归或可变深度迭代
- 动态数组/动态内存
- 非线性数值运算（尤其是浮点）

在这种情况下，“对任意输入证明功能正确性”的验证问题在一般意义上不可判定。实践中只能做到：
- **安全性性质**：不越界、不除零、无溢出、执行时间上界
- **局部正确性**：在输入区间和算法固定条件下，证明近似正确或误差上界

### 1.2 数值计算层面
最小二乘拟合等算法涉及线性系统求解、矩阵运算和浮点误差传播。
即便算法固定，要实现“完整正确性验证”也需要：
- 输入范围（数值域）明确
- 条件数或数值稳定性界限已知
- 误差容忍度可形式化

这类证明可在严格约束下进行，但对通用 DSL 是不可规模化的。

**结论**：扩展 DSL 不可能在“通用计算 + 任意输入 + 自动化”的意义上实现完整验证。

---

## 2. 混合架构的边界设计
### 2.1 DSL 边界（可验证核心）
DSL 负责：
- 状态机与控制逻辑
- 互锁/时序/因果约束
- IO 映射与安全规则
- 轻量的算术与比较（可做静态范围分析）

### 2.2 外部函数边界（计算平面）
外部函数负责：
- 线性代数、拟合、优化、统计等复杂计算
- 动态规模数据处理
- 复杂浮点数值稳定性问题

### 2.3 形式化验证的契约化方式
建议采用 **Assume/Guarantee** 契约：
- DSL 层“假设”外部函数满足接口契约
- 外部函数“保证”满足以下条款（至少满足其一）：
  - 纯函数或显式副作用
  - 运行时间上界
  - 输入范围 -> 输出范围
  - 可失败条件与错误码
  - 数值误差上界（如可提供）

这样可以将不可验证的计算“封装”为可验证接口。

## 3. 数据类型扩展论证
本节按“可验证性 + 实现复杂度 + 价值”三要素评估。

### 3.1 标量类型
#### bool
- **验证性**：极高（有限域）
- **建议**：保留并作为控制逻辑核心

#### int（有界整型）
- **验证性**：高（可通过范围分析/溢出检测）
- **建议**：引入明确位宽（i16/i32），强制溢出策略（饱和/报错）

#### float
- **验证性**：中低（误差传播复杂）
- **建议**：保留，但必须支持：
  - 运行时异常检测（NaN/Inf）
  - 除零检查
  - 可选的区间分析或误差界标签

---

### 3.2 数组（Array）
#### 受限数组（推荐）
**约束**：
- 长度编译期固定
- 索引范围静态可证明
- 禁止动态分配
- 可选：仅允许只读或有限写入

**验证性**：中高（可在静态阶段证明边界安全）
**价值**：支持采样、缓冲、小规模表格

#### 动态数组/切片（不建议入 DSL）
- 索引范围不可静态证明
- 需要运行时边界检查
- 容易引入不可判定性质

**结论**：
数组可进入 DSL，但必须是“编译期固定、索引可证”的受限数组。

---

### 3.3 结构体（Struct）
#### 可引入的结构体类型（推荐）
**约束**：
- 固定字段集合、固定布局
- 字段类型必须是可验证类型（bool/int/float/受限数组/受限结构体）
- 禁止指针、引用、可变长度字段
- 禁止内部持有动态资源（堆分配、外部句柄）

**可验证性**：高（相当于“命名的字段集合”）
**价值**：提高可读性与建模能力，利于 IO/设备数据封装

#### 不建议的结构体特性
- 泛型结构体（增加类型推断与验证复杂度）
- 带动态字段的结构体
- 可变大小结构体

**结论**：
结构体可以引入，但仅限 POD（Plain Old Data）风格。

---

### 3.4 枚举（Enum）
#### 简单枚举（推荐）
- 有限取值集合，可验证性高
- 非常适合状态机和模式表达

#### 复杂枚举（含 payload）
- 若 payload 是可验证类型，可考虑
- 若 payload 含动态数据或外部句柄，不建议

---

### 3.5 Tuple / Record
- 等价于匿名结构体
- 语义简单但可读性差
- 若引入，应限制为固定长度、可验证字段类型

---

### 3.6 字符串（String）
- 字符串引入长度、编码、匹配等复杂验证问题
- 对工业控制核心价值有限

**建议**：
- DSL 内不支持通用字符串
- 仅允许固定长度标识/标签（编译期常量）

---

### 3.7 指针/引用/动态内存
- 直接破坏可验证性边界
- 容易引入别名与生命周期问题

**结论**：不应进入 DSL

---

## 4. DSL 语言子集建议（可验证核心）
### 4.1 类型系统限制
- bool / 有界 int / float
- 受限数组
- POD 结构体
- 简单枚举

### 4.2 控制流限制
- 状态机式控制流（显式 step + goto）
- 仅允许编译期可展开循环（如 repeat N）
- 禁止递归与动态循环

### 4.3 运算限制
- 标量运算 + 有界的数组索引
- 禁止动态分配
- 浮点运算附加运行时检查（NaN/Inf/除零）

---

## 5. 外部函数契约模板（建议）
外部函数必须声明并遵守契约：
- **Pure**：是否纯函数，若有副作用需显式标注
- **TimeBound**：最大执行时间（tick 内）
- **InputRange**：每个参数范围
- **OutputRange**：输出范围或界限
- **Error**：可失败条件与错误返回方式
- **NumericError**：可选的误差界描述

示例：
```
extern function quadratic_fit(...) -> (float, float, float) {
  rust_module: "math::fitting"
  pure: true
  time_bound_us: 50
  input_range: x_i in [-1e3, 1e3], y_i in [-1e6, 1e6]
  output_range: a,b,c in [-1e6, 1e6]
  error: det ~ 0 -> Err("singular")
  numeric_error: <= 1e-3
}
```

---

## 6. 决策建议（简短）
- 若坚持“全局完整验证”，则必须将 DSL 限制为可判定子集，且不支持通用数值计算。
- 若要实用地解决拟合/矩阵类需求，混合架构是成本最低、风险可控的路线。
- 数组与结构体可进入 DSL，但必须是“固定、可验证、无动态资源”的受限版本。
