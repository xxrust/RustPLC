# DSL 已可静态验证时，再用 SIL 验证是否有意义？

日期：2026-02-14

## 结论
即便当前 DSL 已经能做静态验证，“再用 SIL（或 IR）对该程序进行验证”仍然常常有意义；是否值得主要取决于：
1) DSL 静态验证覆盖的语义性质范围；2) DSL→SIL（含运行时/库）这条链路的信任边界与风险。

## 什么时候再用 SIL 验证很有意义
- **要验证的性质比 DSL 静态检查更强/更贴近执行语义**
  - DSL 常见静态验证多聚焦：良构、类型、约束一致性、简单不变量、资源上界等。
  - SIL 层往往更容易表达/证明：堆与别名、跨过程契约、复杂循环不变式、并发/原子性、内存模型相关安全性等。
- **不完全信任 DSL→SIL 的 lowering/优化/插桩**
  - 即便 DSL 端“没问题”，后端生成、优化或封装库调用的过程也可能引入缺陷。
  - 在 SIL 层验证，相当于对更接近执行语义的一层做复核，可捕获“前端通过但后端生成错”的问题。
- **存在外部交互边界（FFI/标准库/运行时）**
  - DSL 静态验证通常需要对外部代码做抽象假设；在 SIL 层更容易把边界条件显式化并验证。
- **工程收益：把 SIL 作为统一的验证后端**
  - DSL 端做轻量前置筛查以提升错误信息与性能；SIL 端复用成熟的 VC/SMT 编码、错误定位与调试能力。

## 什么时候可能更像重复劳动
- **DSL 的静态验证对目标性质“语义完备且实现可信”**，并且还能（或已经）证明：
  - DSL→SIL 保持语义（translation correctness），或至少对关心的性质保持（refinement / property preservation）。
在这种理想条件下，对同一组性质在 SIL 再验证一次，更多是“额外开销”，收益有限。

## 实用折中建议
- **DSL：可读性强的前置筛查**
  - 做良构、简单约束、尽量友好的报错（靠近用户语法与领域概念）。
- **SIL：最终可信的语义验证**
  - 把需要强保证的安全/功能性质落在 SIL 上；
  - 同时把 DSL→SIL 翻译视为潜在缺陷源，用验证覆盖该风险面。

## 需要补充的信息（便于评估“是否值得”）
- 你们 DSL 静态验证当前覆盖的性质清单是什么？
- 你们计划在 SIL 层证明的性质是什么？
- DSL→SIL 过程中是否存在优化/插桩/库封装/并发调度等“可能改变语义或引入 bug”的环节？
