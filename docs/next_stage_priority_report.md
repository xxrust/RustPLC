# RustPLC 下一阶段优先级报告（多子代理多轮讨论版）

日期：2026-02-19

## 1. 讨论方法

本报告基于 3 个“子代理视角”+ 2 轮讨论收敛：

- Subagent-A（安全/控制风险）
- Subagent-B（固件/CI 交付）
- Subagent-C（产品化/开发体验）

讨论流程：

1) Round 1：三方独立给出候选项与排序  
2) Round 2：交叉挑战（“是否真紧急/是否有前置依赖/是否可落地”）后统一排序

## 2. 共识结论（一句话）

下一阶段主线应为：**先做“安全闭环 + 可交付门禁”，再做“体验与平台化”**，而不是继续扩展新功能面。

## 3. 优先级总表

评分规则：
- 重要程度：对安全性、可交付性、长期可维护性的综合影响（1-5）
- 紧急程度：不做会在近期产生显著风险/阻塞的程度（1-5）
- 优先级：P0 > P1 > P2

| 项目 | 重要程度 | 紧急程度 | 优先级 |
|---|---:|---:|---|
| 1) motion + fail-safe 纳入真实板 HIL 常态门禁（含故障注入） | 5 | 5 | P0 |
| 2) Safe-state 异常退出分级验证矩阵（A/B/C/D）+ 关键执行器电气实测 | 5 | 5 | P0 |
| 3) `scenario-doctor` + 错误码 + `--output human/json`（M6） | 4 | 4 | P1 |
| 4) 运行期在线变量/force 控制面（开发态可开关，含审计日志） | 4 | 3 | P1 |
| 5) retain/persistent 变量能力（断电/重启后的语义） | 4 | 3 | P1 |
| 6) 场景资产化（模板库、覆盖策略、`feedback.json`） | 3 | 3 | P2 |
| 7) `rust_plc new` + VS Code 最小扩展 | 3 | 2 | P2 |

## 4. 分项说明（为什么这样排）

### P0-1：HIL 常态门禁（motion + fail-safe）

原因：
- 直接决定“现场可用性”与“上线风险”；
- 当前主 CI 仍以 workspace test / cross-build / PIL 为主，HIL 是 nightly 与 self-hosted 路径，尚未形成主线门禁。

完成定义（DoD）建议：
- 至少 1 套 motion 最小案例 + 1 套 fail-safe 故障案例进入 HIL 稳定回归；
- 失败输出可直接定位到 axis/step/signal。

### P0-2：异常退出分级验证矩阵 + 电气实测

原因：
- “异常退出后是否安全”是高后果风险，且不可只靠文字策略；
- A/B/C/D 退出类型需要区分验证，避免“软件可控退出”结论误套到 crash/kill -9/掉电场景。

完成定义（DoD）建议：
- 每类退出都给出预期、实测、差异解释；
- 关键机构（如垂直电缸刹车、禁能链）给出电气实测记录。

### P1-3：M6 体验硬化

原因：
- 技术能力已较完整，但故障定位成本仍高；
- 这是把“能用”变成“团队可持续用”的最低成本高收益项。

完成定义（DoD）建议：
- 高频错误有统一错误码与修复模板；
- `scenario-doctor` 可给出 fix-preview；
- CLI 支持 `--output human|json` 并覆盖测试。

### P1-4：在线变量/force 控制面（开发态）

原因：
- 当前 force 更偏 SIL 场景脚本，缺少“运行中调试入口”；
- 但该能力会引入安全与审计边界，故不应早于 P0。

完成定义（DoD）建议：
- 默认关闭，显式开关；
- 全量审计日志（谁、何时、改了什么、持续多久）；
- 与回归场景能力不冲突。

### P1-5：retain/persistent

原因：
- 工业 PLC 常见基础能力，影响“重启后行为一致性”；
- 与安全/恢复策略、故障复位流程直接相关。

完成定义（DoD）建议：
- 明确保留变量生命周期与版本策略；
- 提供掉电/重启回放测试与迁移说明。

### P2-6/P2-7：资产化与平台化

原因：
- 价值高，但建立在前述“安全与门禁稳定”之上；
- 属于扩大采用面的工作，不应抢占 P0/P1 的窗口。

## 5. 建议执行节奏（4 周）

- Week 1-2：P0-1（HIL 常态门禁最小闭环）
- Week 2-3：P0-2（异常退出验证矩阵 + 电气实测）
- Week 3-4：P1-3（doctor + 错误码 + 输出模式）

## 6. 风险提示

- 若跳过 P0 直接做平台化，短期看起来“功能很多”，但现场风险与回归可信度会成为后续主要阻塞。
- 若只做 P0 不做 P1-3，团队扩展时会在定位与接入效率上反复损耗。

## 7. 最终建议

下阶段立项建议按以下顺序推进：

1. P0-1  
2. P0-2  
3. P1-3  
4. P1-4 / P1-5（并行评审，串行落地）  
5. P2-6 / P2-7
