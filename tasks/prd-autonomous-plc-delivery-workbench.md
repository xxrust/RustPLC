## 1. Introduction

The Autonomous PLC Delivery Workbench is a desktop-style engineering workspace for reviewing PLC projects generated by agents without human editing during the generation run.

The delivery project is the primary unit of work. Each project exposes the complete chain from authored process intent to generated source, compiler semantics, verification evidence, wiring instructions, simulation or HIL evidence, human safety hold points, and release authorization.

Compiler progress is visible through the behavior of real delivery projects. Every project shows which compiler stages were exercised, which artifacts were produced, which tests passed, and where a compiler capability remains blocked. The product does not add a separate compiler-monitor dashboard.

The interaction model follows Cursor and VS Code: activity bar, project explorer, editor groups, dockable inspectors, bottom panels, command palette, and a persistent status bar. The interface is a workstation, not a vertically scrolling Web dashboard.

## 2. Core Model

### 2.1 Evidence Chain

```text
system contract / process intent
              |
              v
agent definition + input manifest + skill versions
              |
              v
unattended agent run + retries + anomalies + corrections
              |
              v
DSL source -> semantic IR -> verification -> runtime/codegen
              |
              v
wiring plan -> point check -> no-board/HIL -> observed trace
              |
              v
human safety holds -> electronic sign-off -> release verdict
```

### 2.2 Independent Status Axes

The UI keeps evidence state and responsibility state separate.

| Axis | Canonical states | Meaning |
| --- | --- | --- |
| Evidence | `authored`, `derived`, `verified`, `observed`, `warning`, `blocked` | What kind of evidence supports the claim |
| Responsibility | `agent_running`, `agent_complete`, `human_action_required`, `human_confirmed`, `release_approved` | Who owns the next action |

A green verification result never implies that physical wiring or release approval is complete.

### 2.3 Compiler Evidence Inside a Project

Every delivery run records the compiler stages it exercised:

```text
Parser -> AST -> Semantic -> IR
                         |-> Safety
                         |-> Liveness
                         |-> Timing
                         |-> Causality
                         |-> Runtime Bridge / Simulation / HIL
                         `-> Codegen
```

Each stage exposes a status, artifact reference, source commit, digest, test or CI run, diagnostics, and blocker reason. The frontend renders compiler-owned evidence and does not infer PLC correctness.

## 3. Goals

- Prove whether a generation run completed without human source edits.
- Expose every agent retry, anomaly, correction, and final file change in chronological order.
- Let an engineer inspect PLC source, topology, task flow, IR, verification, runtime evidence, and codegen output in one workspace.
- Generate a reviewable wiring plan with explicit human point-check and safety hold states.
- Require electronic sign-off for physical wiring, safety review, and release approval.
- Derive project status from Git, compiler artifacts, tests, CI, simulation, HIL, and signed human evidence.
- Let the RustPLC compiler engineer assess compiler maturity through real project coverage and failures.
- Preserve a dense Cursor/VS Code-style desktop interaction model at common engineering display sizes.

## 4. Primary Users

- RustPLC compiler engineer: reviews compiler behavior across real delivery projects and traces failures to a compiler stage.
- Control engineer: reviews generated PLC logic, topology, I/O mapping, fault paths, and codegen output.
- Electrical or commissioning engineer: executes wiring and point-check tasks and attaches observed evidence.
- Safety reviewer: reviews formal verification, physical validation, unresolved blockers, and release holds.
- Release approver: signs the final release verdict after all required evidence is present.

## 5. Information Architecture

### 5.1 Application Shell

The shell uses the following stable regions:

- Title and command center: workspace name, project name, command palette, global search.
- Activity bar: Projects, Agent Runs, Wiring, Verification, Evidence, Search, Source Control.
- Primary sidebar: context-specific tree, filters, saved views, and project files.
- Editor area: source files, topology, semantic flow, agent timeline, wiring map, verification report, trace replay.
- Secondary sidebar: evidence inspector, provenance, selected-node details, and hold-point status.
- Bottom panel: Problems, Tests, Verification, Terminal, Output, Audit Log.
- Status bar: Git commit, workspace cleanliness, agent run, compile stage, verification summary, HIL state, human holds.

### 5.3 Compiler Progress Without a Separate Dashboard

Compiler maturity is exposed through the project workspace:

- The Problems panel aggregates compiler diagnostics and blockers across opened delivery projects.
- The Tests panel groups results by compiler stage and project fixture.
- Project Explorer badges show the last verified commit and evidence freshness.
- Search and command palette support queries such as `stage:codegen status:blocked` or `diagnostic:SEM-110`.
- The status bar shows the active project's latest complete pipeline.
- A workspace-level evidence query can aggregate results, but it remains a project-corpus view rather than a separate monitoring product.

### US-002: Prove an Unattended Agent Run

**Description:** As a reviewer, I want to inspect the immutable inputs and execution provenance of an agent run so that I can determine whether humans edited generated source during the run.

**Acceptance Criteria:**

- [ ] The run records model, agent identities, task definitions, skill versions, tool versions, start and end times, Git base commit, and input manifest.
- [ ] The run records every generated or modified file with before and after digests.
- [ ] Human-authored changes detected between run start and completion are reported as `human_intervention_detected`.

## 7. Functional Requirements

1. FR-1: The server must expose a stable registry of delivery projects rather than treating examples as projects.
2. FR-2: A delivery project must declare its layer, source entry, system contract, scenario roots, and evidence roots.
3. FR-3: Every agent run must have a stable run ID, immutable input manifest, provenance record, event timeline, file digest set, and final verdict.
4. FR-4: The system must detect and report source changes that cannot be attributed to the recorded agent run.
5. FR-5: Agent anomalies and corrections must remain first-class auditable records.
6. FR-6: Compiler stage status must be project-scoped and backed by compiler, test, CI, or blocker artifacts.
7. FR-7: The UI must render compiler-owned diagnostics and verdicts without implementing PLC semantics in TypeScript.
8. FR-8: Wiring artifacts must be derived from controller profiles, I/O aliases, topology, and declared device ports.
9. FR-9: Physical point checks must remain separate from formal verification status.
10. FR-10: Human holds must support electronic signatures and evidence-digest invalidation.
11. FR-11: Release approval must require all configured verification, execution, wiring, and human-hold gates.
12. FR-12: Existing harness runs, including `input-manifest.json`, `result.json`, traces, and reports, must be importable into a delivery project.
13. FR-13: The desktop shell must use activity bar, sidebars, editor groups, bottom panel, command palette, and status bar.
14. FR-14: Project overview content must appear as an editor surface or inspector, not a scrolling card dashboard.
15. FR-15: Cross-project compiler progress must be available through Problems, Tests, Search, and evidence queries inside the workbench.
16. FR-16: The product must not add a standalone compiler-monitor status page.
17. FR-17: All evidence links must support deep-linking to the owning project, run, artifact, semantic object, and source revision.
18. FR-18: Status colors must be paired with icons and text labels.
19. FR-19: The server must enforce authentication and role-based authorization before electronic signing is enabled.
20. FR-20: Audit records must be append-only from the Web API perspective.

## 9. Design Brief

### 9.1 Feature Summary

Build one integrated PLC delivery workstation. The workspace lets engineers move from system intent to agent provenance, source, topology, verification, wiring, HIL evidence, and human release holds without leaving the project context.

### 9.2 Primary User Action

The primary action is selecting an engineering object or problem and tracing it through source, compiler semantics, execution evidence, physical wiring, and responsibility status.

### 9.3 Visual Direction

- Color strategy: Restrained dark product palette with cyan selection, amber warning, red blocked, and green verified roles.
- Scene: An engineer uses a high-density workstation in a control-development environment, moving repeatedly between code, topology, evidence, and terminal output.
- Anchor references: VS Code for shell anatomy and panel docking; Cursor for agent-run and diff workflows; industrial PLC engineering software for evidence density and explicit status.
- Selected probe direction: VS Code source-first shell plus assurance-first topology and evidence inspector. Agent Timeline is a dockable editor tab and bottom-panel view.

### 9.4 Layout Strategy

- Full viewport application shell with no page-level vertical document flow.
- Stable activity bar and project explorer anchor the left side.
- Editor groups own the central work surface.
- Evidence inspector owns provenance and selected-object facts on the right.
- Problems, Tests, Verification, Terminal, Output, and Audit Log share the bottom panel.
- Status bar keeps current project, Git, compile, verification, HIL, and hold state visible.
- Resizing changes pane allocation and collapse behavior, not typography scale.

### 9.5 Key States

- No workspace: open or register a delivery project.
- Project loading: skeleton tree, editor placeholder, evidence loading state.
- Agent running: live timeline, current task, elapsed time, output stream, pending verdict.
- Agent complete: immutable run summary, digests, anomalies, corrections, unattended verdict.
- Evidence stale: source revision and artifact revision differ.
- Verification blocked: stage, diagnostic, dependency, and resolution condition shown.
- Human action required: named hold, responsible role, required evidence, sign action.
- Release approved: signed revision and evidence digest set shown.
- Partial backend or CI outage: cached evidence labeled with freshness and unavailable source.

### 9.6 Interaction Model

- Single click selects; double click pins an editor tab.
- Context menus provide artifact-specific commands.
- Command palette searches projects, files, runs, diagnostics, semantic objects, and holds.
- Problems and evidence links navigate to the exact owning object.
- Hover provides short provenance; the secondary sidebar provides the complete record.
- Keyboard commands cover open, search, panel toggle, editor split, next problem, and evidence navigation.
- Electronic signing uses an explicit confirmation dialog containing revision, digest set, decision, and responsibility statement.

### 9.7 Content Requirements

- Status labels use canonical evidence and responsibility vocabulary.
- Every verdict exposes its producer, timestamp, source revision, and artifact link.
- Agent events use concrete task and tool names.
- Wiring uses semantic alias and physical terminal side by side.
- Error messages name the failed stage, affected object, diagnostic code, and next validation action.
- Empty states explain which artifact or action will populate the view.

### 9.8 Recommended Implementation References

- `impeccable/reference/layout.md` for resizable multi-pane structure.
- `impeccable/reference/interaction-design.md` for command palette, keyboard flows, and evidence navigation.
- `impeccable/reference/harden.md` for loading, stale-data, signing, CI outage, and authorization states.

## 10. Technical Considerations

- Reuse the existing Web UI editor, topology canvas, flowchart review, run, replay, diagnosis, audit, and geometry components inside the new desktop shell.
- Replace the example-template project list with a delivery-project registry while retaining examples as a separate catalog.
- Use `geometry` artifacts for topology, task flow, and evidence overlays.
- Extend harness output with stable project, agent, anomaly, correction, Git, CI, and signature schemas.
- Bind all run and artifact records to `project_id`, `source_commit`, and content digests.
- Implement the missing server authentication contract before enabling signatures.
- Keep local and CI result schemas compatible so the same panel can render both.
- Preserve append-only audit semantics and validate artifact paths against the workspace root.
- Add import support for the existing complex self-test specimen as the first canonical delivery fixture.

## 11. Non-Goals

- Project ranking, scoring, or side-by-side competition.
- A standalone compiler-monitor dashboard.
- A marketing-style homepage or card-grid analytics dashboard.
- Mobile-first editing or phone-based project review in the first release.
- Frontend reimplementation of compiler, verification, or wiring semantics.
- Automatic human safety approval.
- Claims that simulation or formal verification proves physical wiring correctness.
- CAD, electrical field solving, collision physics, or high-fidelity physical digital twins.
- An AI chat screen as the primary product surface.

## 12. Success Metrics

- An engineer can determine within 60 seconds whether an agent run was unattended and open the supporting evidence.
- An engineer can locate the compiler stage responsible for a project blocker within 60 seconds.
- An electrical engineer can identify every unverified I/O point without reading PLC source.
- A safety reviewer can distinguish formal verification, observed execution, and human confirmation for every release gate.
- A source or artifact digest change invalidates stale evidence and signatures automatically.
- The existing complex self-test specimen is fully browsable without manually copying data into the UI.
- Common workflows complete without leaving the desktop shell or navigating a vertically scrolling page.
- The interface passes build, lint, WCAG 2.1 AA checks, and real-browser verification at 1440x900 and 1920x1080.

## 13. Open Questions

- Whether electronic signatures in the first release are internal engineering attestations or must satisfy a specific regulatory signature standard. The first implementation should treat them as attributable engineering attestations until a regulatory requirement is named.
