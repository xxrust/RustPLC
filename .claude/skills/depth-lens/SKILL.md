# depth-lens

识别问题的认知深度，向第一性原理方向追问一层。

---

## 七层模型

| 层级 | 名称 | 特征 | 典型问题形态 |
|------|------|------|-------------|
| L1 | 应用层 | 怎么用、怎么配、怎么调 | "这个 API 怎么调用" |
| L2 | 学科层 | 属于哪个领域、遵循什么规范 | "这符合 IEC 61131-3 吗" |
| L3 | 原理层 | 为什么这样设计、背后的工程原理 | "为什么 PLC 用扫描周期而不是事件驱动" |
| L4 | 概念层 | 核心抽象是什么、边界在哪 | "状态机和流程图的本质区别是什么" |
| L5 | 关系层 | 概念之间如何约束、如何耦合 | "安全性和活性为什么不能同时最优" |
| L6 | 机制层 | 约束背后的因果机制是什么 | "为什么形式化验证能证明安全而测试不能" |
| L7 | 本质层 | 第一性原理、不可再分的基础事实 | "计算的本质是状态变换，安全的本质是可达集有界" |

---

## 执行规则

1. 读取用户的问题，判断它当前处于哪一层（L1-L7）。
2. 用一句话标注当前层级。
3. 给出一个向下一层追问的回答（不超过 3 段）：
   - 第一段：回答用户当前层级的问题（不能跳过，先解决眼前的事）
   - 第二段：指出这个问题在更深一层的本质是什么
   - 第三段：抛出一个更深层的追问，引导用户思考
4. 如果用户已经在 L7（本质层），不再向下追问，改为横向关联——找一个看似无关但共享同一第一性原理的领域做类比。

---

## 格式

```
[L{n} {层名}] {一句话定位}

{回答当前问题}

{更深一层的洞察}

> 追问：{引导性问题}
```

---

## 示例

用户问："基恩士的 FB_Cylinder 和我们的 extend/retract 有什么区别？"

```
[L3 原理层] 两种气缸抽象的设计原理对比

基恩士的 FB_Cylinder 是常驻运行时守护者——每个扫描周期都检查传感器一致性、超时、模式匹配，不依赖工站流程是否在运行。你们的 extend/retract 是声明式闭环——编译器证明 task 逻辑不会违反安全约束，但运行时没有独立于 task 的设备监控层。

更深一层看，这是两种安全保证范式的对比：运行时防御（检测到违规后反应）vs 编译期证明（证明违规不可达）。前者的覆盖面更广（能处理硬件故障），后者的保证更强（数学证明而非概率检测）。工业系统需要两者共存——编译期证明正常路径安全，运行时防御异常路径。

> 追问：如果编译期已经证明了"不可能在不安全状态下执行动作"，运行时监控还有什么不可替代的价值？它防御的是什么类型的故障？
```

---

## 边界

- 不改变用户的原始任务。先解决问题，再追问深度。
- 追问是可选的——如果用户明确在赶进度（"快速修一下"、"帮我改这行"），只标注层级，不展开追问。
- 不要在每轮对话都追问。如果上一轮已经追问过且用户没有接话，本轮只标注层级。
- 对纯操作性任务（git commit、文件重命名、格式化）不激活。
