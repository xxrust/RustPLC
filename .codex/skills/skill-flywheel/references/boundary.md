# 源码边界

## 这个 skill 能做什么

这个 skill 可以帮你建立一套有纪律的“禁止读源码”流程：

- 把真实目标 skill 当作默认公开输入
- 在必要时额外导出显式辅助工件
- 明确要求某个 agent 只能在这层输入边界内工作
- 记录越界需求和痛点
- 让另一个可读源码的 agent 负责诊断根因
- 让整轮研究尽量通过落盘工件而不是会话记忆推进

## 这个 skill 不能保证什么

这里的关键边界是：默认公开物只有真实目标 skill 本身。仓库里的 `README`、`docs`、`examples` 等文件，除非被显式导出为辅助工件，否则都不属于盲测执行者可读输入。

`public/` 目录只用于承载显式导出的辅助工件，不用于把仓库里的普通文件直接“抄出来当公开面”。

还要区分两种盲测方式：

- `clean-room`
  由外部编排器开启全新顶层对话，只注入本轮允许的工件。这才是高可信盲测。
- `weak-blind`
  在当前主对话里开子 agent，或使用其他共享会话状态的方式。它可能减少一部分历史污染，但仍不等于全新对话。

`weak-blind` 可以用于低成本探索，但不能和 `clean-room` 的证据强度混为一谈。

## 实操规则

对于禁止读源码的执行者：

1. 读取真实目标 skill。
2. 读取 `context/program.md` 和 `context/task.md`。
3. 如果存在，再读取生成出的 `public/` 目录。
4. 不要查看目标 skill 之外的仓库文件，包括 `README`、`docs/`、`examples/`、`src/`、`crates/` 或其他受保护路径。
5. 如果必要信息缺失，就把它记成痛点，不要直接越界。

对于研究编排者：

1. 如果你只能在当前会话里开子 agent，请把本轮结果标记为 `weak-blind`。
2. 如果你能用外部系统重启全新对话，并且只注入本轮工件，才把本轮结果标记为 `clean-room`。
3. 不要把 `weak-blind` 的成功误写成“已经完成高可信盲测”。
4. 如果你连子 agent 都不能或不应启动，可以用单代理 fallback：
   - 先按 blind-runner 边界做观察并写 `logs/pain-points.*`
   - 再恢复可读源码权限做 root-cause 与 decision
   - 在决策里明确说明本轮为何只能做到 `weak-blind`

对于可读源码的分析者：

1. 只有在盲测结束后才使用源码。
2. 明确说明问题更适合暴露成哪一种东西：
   - skill 指令
   - 辅助工件
   - 代码 / CLI / 诊断能力

## 如果你需要更强隔离

如果你需要更强的执行隔离，请把 Agent 2 放到一个单独工作区里，并且只放入：

- 真实目标 skill
- 显式导出的 `public/` 辅助工件包

这个 skill 支持这种工作流，但它本身无法强制实现。
