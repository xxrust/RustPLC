# 分类规则

默认只用这四个标签。除非项目有很强的理由，否则不要额外发明新标签。

## `skill-gap`

当盲测执行者拿到的目标 skill、研究程序与显式导出的辅助工件已经足够，但目标 skill 仍然没能：

- 选对工作流
- 问对下一个关键问题
- 正确理解现有工件
- 应用已经公开的项目约定

就归为 `skill-gap`。

修复方式：

- 修改目标 skill
- 改动保持最小、偏流程化
- 必要时同步收窄下一轮研究程序

## `public-surface-gap`

当盲测执行者需要某个本应无需看源码就能获得的稳定事实，但系统没有把它显式导出成辅助工件，而是只能埋在仓库文件里时，就归为 `public-surface-gap`。

常见例子：

- 导出的命令矩阵
- 导出的子命令清单
- 生成出的输入输出示例
- 机器可读 manifest
- 明确导出的帮助信息或报告

修复方式：

- 新增或改进显式辅助工件
- 不要把仓库里的普通文档直接当成公开面转交给盲测执行者
- 除非 skill 还需要额外的选择规则，否则不要把同样的细节再抄进 skill

## `code-gap`

当产品本身对外暴露的能力就缺失或太弱，以至于就算 skill 很好、显式辅助工件也很好，任务仍然做不成时，就归为 `code-gap`。

常见例子：

- 缺少稳定 CLI 帮助
- 缺少诊断
- 报告格式不稳定或不存在
- 不读源码就无法知道系统支持什么能力

修复方式：

- 修改代码库、CLI 或生成报告能力
- 在 `logs/decision.md` 里明确写明“问题不应继续由 skill 承担”

## `task-ambiguity`

当任务本身描述不清，盲测执行者缺少只有用户才能给出的关键信息时，就归为 `task-ambiguity`。

修复方式：

- 改进任务表述
- 只追问真正阻塞的更窄问题
- 调整下一轮研究程序，不要带着模糊任务继续跑

## 冲突时怎么判

如果一个事实是稳定的、对外有用的，并且应当被显式导出给盲测执行者，优先判成 `public-surface-gap`，而不是 `skill-gap`。

如果一个事实没有对外暴露，是因为产品本身根本没提供这项外部能力，优先判成 `code-gap`，而不是 `skill-gap`。
